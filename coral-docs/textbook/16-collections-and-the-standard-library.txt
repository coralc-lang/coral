Chapter 16

Collections and the Standard Library

A Language Without a Library Is a Set of Keywords

Here is a thought experiment. Take away every library from the language you use most. No arrays that grow, no strings that build, no maps, no files, no printing, no math beyond arithmetic. What is left? A set of keywords and a way to move bytes around. Everything that makes the language useful to a human being — the container that holds a list whose length is unknown, the text buffer that accumulates a message, the lookup table that turns a name into a value — lives in the standard library. The language is the grammar; the library is the vocabulary.

Coral's standard library is deliberately organised around one idea, and if you understand the idea you will always know where a tool lives. The idea is that a module groups a capability, and the tree of modules is a tree of capabilities. Under the root `std` sit `collections`, `text`, `io`, `fmt`, `math`, `memory`, `crypto`, `concurrent`, `parser`, `data`, and `testing`. Under `collections` sit the individual structures: `vec`, `map`, `hashmap`, `set`, `queue`, `deque`, `ringbuf`, `priorityqueue`, `linkedlist`, `tree`, `trie`, `bitset`, `cache`, `iter`, `sort`. You never have to guess; you only have to ask "what kind of thing am I doing?" and walk to that branch.

There is one more distinction, and it is worth stating before the first type. `std` is the portable surface — the same names and signatures on every platform. `core` is what the language itself is built from: `str`, `cchar`, `char_util`, and the numeric limits in `core::limits`. A normal program imports from `std` and never thinks about `core`. `platform` wraps the operating system (on Linux, the libc surface) and is reached only when a program is deliberately doing something close to the metal. And because two types are so common that they deserve short names, the root re-exports them: `std::option` is `std::data::option` and `std::result` is `std::data::result`. The three most-used containers get the same treatment.

Hold on — let me say that more plainly, because it is the key to reading every import in this book. The library is a tree, but a few leaves are also hung near the root so you do not have to climb. When you write:

    import(lib) std::vec { Vec };
    import(lib) std::option { Option };
    import(lib) std::result { Result };

you are using three shortcuts. The full paths — `std::collections::vec`, `std::data::option`, `std::data::result` — are exactly equivalent, and this chapter uses the full path wherever it clarifies which branch a type comes from, because knowing where a type lives is half of knowing what it does.

16.1 Vec<T>: The Dynamic Array

Vec<T> is the workhorse of the whole library, and it is worth understanding it completely, because a great deal of everything else is built on top of it or modelled after it.

Start with the familiar problem. You are reading records from a file and you do not know in advance how many there are. A fixed array cannot hold them because you do not know the size. A linked list could, but then every read hops across the heap and the cache hates you. What you want is an array that starts small and grows itself when it runs out of room. That is a Vec.

Here is its actual declaration, quoted from `std::collections::vec`, fields and all:

    pub struct Vec<T> {
        T*    data;
        usize len;
        usize cap;
    }

The three fields tell the entire story. `data` points at a heap allocation of `cap` slots. `len` is how many of those slots currently hold live elements. `cap` is how many slots the allocation has room for. The elements occupy `data[0]` through `data[len - 1]`; the slots from `len` to `cap` exist but are not part of the vector's value yet. Every operation Vec supports is bookkeeping on those three numbers, and because the fields are public — which is a deliberate design choice, not an accident — a Vec is a documented data structure rather than an opaque box. You can always ask what it costs in memory, because the numbers that say so are right there.

You create one in one of two ways. `new` makes an empty one with no allocation at all, and `withCap` allocates room for a known number of elements up front:

    import(lib) std::vec { Vec };

    Vec<i32> a = Vec<i32>::new();
    Vec<i32> b = Vec<i32>::withCap(1024);

`new` costs nothing until you push, at which point the first push allocates a small default capacity. `withCap` allocates immediately, which matters when you already know roughly how many elements are coming: allocate once and push a thousand times, instead of reallocating and copying seven times as the buffer doubles.

The core operations read like a sentence:

    Vec<i32> v = Vec<i32>::new();
    v.push(10);                 // append to the end
    v.push(20);
    v.push(30);

    i32 last = v.pop();         // 30; removes and returns the last
    usize n  = v.count();       // 3 before the pop, 2 after
    bool e   = v.isEmpty();     // count() == 0

`push` appends, and when `len` has caught up with `cap` it calls `reserve`, which doubles the capacity (or uses 4, for the very first growth) and copies the old elements into the new allocation. `pop` removes and returns the last element; it is an out-of-bounds trap if the vector is empty, so guard with `isEmpty` when you are not sure. `count` reports `len` — it is named `count` rather than `len` so that the method and the field never collide — and `isEmpty` is the readable spelling of `count() == 0`.

Element access comes in several forms, and the names tell you the trade-off. `at` returns an element by value with a bounds check; `set` writes one; `atPtr` and `atConst` return a mutable and a const pointer to a single element; `ptr` and `constPtr` return a pointer to the whole backing array:

    v.set(0, 99);                     // v[0] = 99
    i32 x = v.at(0);                  // bounds-checked read, by value
    i32* p = v.atPtr(1);              // pointer to element 1
    const i32* cp = v.atConst(1);     // const pointer to element 1
    i32* base = v.ptr();              // the whole array
    const i32* cbase = v.constPtr();  // the whole array, read-only

The distinction between an index-based and a pointer-based access is a theme of the whole library. `at` is checked and is the default; `atPtr` is the unchecked form you reach for inside a loop that has already established the bound, when you want to skip a check you have already paid for. Because the unchecked form has its own name, an unchecked access is a visible decision in the code rather than an invisible optimisation.

Moving elements around is a first-class concern:

    v.insert(0, 5);            // shift right, put 5 at the front
    v.removeAt(0);             // shift left, drop the front
    v.removeRange(1, 3);       // remove elements [1, 3)
    v.fill(7);                 // every element becomes 7
    v.reverse();               // in place
    v.clear();                 // len = 0; the allocation is kept

`insert` and `removeAt` are O(n) because they shift the tail, which is the honest cost of keeping elements contiguous. `clear` frees nothing; it simply sets `len` back to zero so the existing allocation can be reused, which is exactly what you want in a loop that refills the same buffer.

A handful of methods make a Vec act like an ordered sequence:

    bool sorted = v.isSortedBy(less);          // bool(T, T) less
    v.sortBy(less);                            // in-place quicksort
    i64 where = v.binarySearchBy(key, cmp);    // index, or -1

`sortBy` takes a `bool(T, T)` predicate meaning "a comes before b", and `binarySearchBy` takes an `i32(T, T)` comparator returning negative, zero, or positive. The generic sort in `std::collections::sort` and the typed sorts `sortI32`, `sortF64`, and `sortusize` are built around the same idea; we meet them in 16.12.

Finally, capacity management, which is how you turn a Vec from convenient into fast:

    v.reserve(4096);           // grow to at least 4096
    v.reserveExact(4096);      // grow to exactly 4096
    v.shrinkToFit();           // shrink the allocation to len
    v.dispose();               // free the backing array now

`shrinkToFit` is the method to call when a Vec has finished growing and may live a long time; it releases the slack that doubling left behind. `dispose` frees the array immediately, and `drop` — which Vec conforms to through `@drop` — calls `dispose` for you when the value goes out of scope. You rarely call `dispose` by hand; you let the value die, and the compiler schedules the free. That is the RAII rule of Chapter 11, specialised to the container.

Iterate a Vec either by index or by range-for:

    for (usize i = 0; i < v.count(); i += 1) {
        println("{}", v.at(i));
    }

    for (i32 value : v) {
        println("{}", value);
    }

The range-for form is the idiomatic read: it visits each element once, in order, and hides the index. Reach for the indexed form only when you need the index itself.

16.2 Arr<T, N>: Fixed Size, Inline Storage

Vec grows. `Arr<T, N>` is its fixed-size sibling: the length is part of the type, known at compile time, and the storage lives inline in the value rather than behind a pointer.

    import(lib) std::arr { Arr };
    Arr<i32, 4> location = Arr<i32, 4> { 1, 2, 3, 4 };

Because `N` is a compile-time constant, the compiler can check every constant index into an Arr, so an out-of-range constant is a build error rather than a runtime trap. The API mirrors Vec's access methods: `ptr`, `constPtr`, `count`, `isEmpty`, `at`, `set`, `atPtr`, `front`, `back`, `fill`, `copyTo`, and `copyFrom`:

    location.set(0, 9);
    i32 first = location.front();
    i32 last  = location.back();
    i32 buf[4];
    location.copyTo(buf);          // copy every element out
    location.copyFrom(buf);        // copy every element in

This is the container to reach for when the size is genuinely fixed — a three-component vector, a 2x2 matrix, a fixed header — because it needs no heap allocation and its size is a fact the compiler can use. A plain Coral array written `T name[N]` is the same storage without the methods; Arr is the array with the container interface attached.

16.3 Map<K, V>: The Ordered Associative Container

A map associates keys with values. Coral's ordered map is an AVL tree, and the choice to make it ordered is a promise: iteration is deterministic, in key order, and range-shaped queries are possible. The price is O(log n) per operation instead of the O(1) a hash table gives.

The declaration shows why the API looks the way it does:

    pub struct Map<K, V> {
        MapEntry<K, V>* root;
        usize len;
        i32(K, K) cmpFn;
        bool failed;
    }

The map does not know how to compare two keys of an arbitrary type `K`; it is handed a comparator at construction. The comparator is `i32(K, K)`, returning negative, zero, or positive, exactly the convention `qsort` and `strcmp` use:

    import(lib) std::collections::map { Map };

    i32 cmpStr(str a, str b) { return a.compare(b); }

    Map<str, i32> ages = Map<str, i32>::new(cmpStr);
    ages.insert("ada", 36);
    ages.insert("grace", 45);

    if (ages.contains("ada")) {
        Option<i32> a = ages.get("ada");
        println("ada = {}", a.unwrap());
    }
    ages.remove("grace");

Two things are worth pausing on. First, `insert` returns a `Result<V, CollectionError>`, because the AVL tree allocates a node and allocation can fail; the `CollectionError` variant has an `AllocFailed` case. You may ignore the result when you are confident, but the library does not pretend a fallible operation cannot fail. Second, `get` returns an `Option<V>`, the same honest "a value, or nothing" from Chapter 15:

    Option<i32> maybe = ages.get("ada");
    if (maybe.isSome()) {
        i32 a = maybe.unwrap();
    }
    i32 definitelyThere = ages.get("ada").unwrapOr(-1);

When you want to modify a value in place rather than copy it out, `getPtr` hands you an `Option<V*>`:

    Option<i32*> slot = ages.getPtr("ada");
    if (slot.isSome()) {
        *slot.unwrap() = *slot.unwrap() + 1;   // increment in place
    }

Because a Map is ordered, iteration is in key order, and it is done with the `each` method rather than a range-for, because the map exposes no iterator of its own:

    void printAge(str key, i32 value) {
        println("{} = {}", key, value);
    }
    ages.each(printAge);

The function passed to `each` receives the key and the value and returns nothing. This is the standard Coral way to walk a container that is not a Vec or an Arr: hand it a function, not a cursor.

16.4 The Hashed Maps: HashMap and UnorderedMap

The ordered map keeps an O(log n) promise and keeps your keys sorted. When you do not need order and you do want speed, you want a hash table. `HashMap<K, V>` is a linear-probing hash table whose average operations are O(1):

    pub struct HashMap<K, V> {
        HashMapEntry<K, V>* entries;
        usize cap;
        usize len;
        usize(K) hashFn;
        bool(K, K) eqFn;
    }

Hashing needs two functions a generic container cannot invent: a hash and an equality test. You supply both, which means you decide what "the same key" means:

    import(lib) std::collections::hashmap { HashMap };

    usize hashStr(str k) {
        usize h = 5381;
        for (usize i = 0; i < k.len; i += 1) h = h * 33 + (usize)k.ptr[i];
        return h;
    }
    bool eqStr(str a, str b) { return a.equals(b); }

    HashMap<str, i32> counts = HashMap<str, i32>::new(hashStr, eqStr);
    counts.insert("apple", 3);
    counts.insert("pear", 1);

The API is close to Map's: `insert` (returning a `Result`), `get` and `getPtr` (returning an `Option`), `contains`, `remove`, `removeEntry`, `clear`, `count`, `isEmpty`, `each`, and `eachEntry`. It adds one thing the ordered map does not offer cheaply: bulk key and value extraction.

    Vec<str> keys   = counts.keys();
    Vec<i32> values = counts.values();

    void report(str key, i32 value) { println("{}: {}", key, value); }
    counts.each(report);

`UnorderedMap<K, V>` is a thin wrapper with one purpose: to say in the type that iteration order is not a promise. It is built on `HashMap` and forwards every operation, but because it is a distinct type, nobody downstream can accidentally depend on an order that was never guaranteed.

    import(lib) std::collections::unordered_map { UnorderedMap };
    UnorderedMap<str, i32> cache = UnorderedMap<str, i32>::new(hashStr, eqStr);

The three-map split is a small example of a large principle in the library: when two behaviours differ, they are two types with two names, not one type with a flag. A flag would let a caller depend on an order a HashMap never promised; two types make the promise explicit in the signature of every function that accepts one.

16.5 Set<T>

A set is a map without values. It answers "is this present?" and enforces uniqueness. Coral's `Set` is a `HashMap<T, bool>` underneath, and it needs the same two functions:

    pub struct Set<T> {
        HashMap<T, bool> inner;
        usize(T) hashFn;
        bool(T, T) eqFn;
    }

    import(lib) std::collections::set { Set };

    Set<str> seen = Set<str>::new(hashStr, eqStr);
    seen.insert("apple");
    seen.insert("banana");
    seen.insert("apple");          // no effect; already present

    if (seen.contains("apple")) { ... }
    seen.remove("banana");
    seen.each(printStr);

Sets are the natural tool for deduplication, membership, and the set algebra that shows up in data work. The library provides the algebra directly:

    Set<str> a = Set<str>::new(hashStr, eqStr);
    Set<str> b = Set<str>::new(hashStr, eqStr);
    // ... fill both ...

    Set<str> both  = a.union(&b);
    Set<str> share = a.intersection(&b);
    Set<str> onlyA = a.difference(&b);
    bool aInB      = a.isSubset(&b);
    bool aCoversB  = a.isSuperset(&b);
    Vec<str> asList = a.toVec();

A common pattern — print each distinct word of a text — is a Set in a few lines:

    Set<str> words = Set<str>::new(hashStr, eqStr);
    for (str w : splitVec(text, ' ')) {
        words.insert(w);
    }
    words.each(printStr);

Choosing between a Set and a Vec-with-a-scan is a question of size. For a handful of items the scan is faster and simpler; for thousands, the set's average O(1) membership wins by orders of magnitude.

16.6 Queue, Deque, and RingBuf

Order matters as much as membership, and different orders call for different structures. `Queue<T>` is first-in-first-out, and it is a thin wrapper over Deque that deliberately exposes only one end:

    pub struct Queue<T> {
        deque::Deque<T> inner;
    }

    import(lib) std::collections::queue { Queue };

    Queue<i32> q = Queue<i32>::new();
    q.enqueue(1);
    q.enqueue(2);
    q.enqueue(3);
    i32 first = q.dequeue();       // 1 — FIFO
    i32 front = q.peek();          // 2, without removing

    usize n = q.count();
    bool empty = q.isEmpty();
    q.clear();

`Deque<T>` is a double-ended queue: a growable ring that supports both ends. It is the structure for a work list that grows at both ends and for a sliding window:

    import(lib) std::collections.deque { Deque };

    Deque<i32> d = Deque<i32>::new();
    d.pushBack(2);
    d.pushFront(1);
    i32 left  = d.popFront();      // 1
    i32 right = d.popBack();       // 2
    i32 at    = d.at(0);           // random access by logical index
    d.set(0, 9);

`RingBuf<T>` is a fixed-capacity ring: a queue whose storage is a fixed array with head and tail indices that wrap. It never allocates after construction, and when it is full, pushing overwrites the oldest element — which is precisely the behaviour you want in a logging buffer or a recent-history window:

    import(lib) std::collections.ringbuf { RingBuf };

    RingBuf<f64> samples = RingBuf<f64>::new(1024);
    samples.push(sample);          // overwrites the oldest once full

    usize held = samples.count();
    bool full  = samples.isFull();
    f64 oldest = samples.front();
    f64 newest = samples.back();

The overlap among Queue, Deque, and RingBuf is intentional. Queue is the simplest one-ended interface; Deque adds the other end; RingBuf adds a size bound and the no-allocation guarantee. Pick the one whose constraints you actually need, so the type documents the constraint for the reader.

16.7 PriorityQueue<T>

A priority queue always hands you the smallest element — or, with a comparator that reverses the order, the largest. It is a binary heap over a Vec's worth of storage:

    pub struct PriorityQueue<T> {
        T* data;
        usize len;
        usize cap;
        bool(T, T) less;
    }

    import(lib) std::collections::priorityqueue { PriorityQueue };

    bool lessI32(i32 a, i32 b) { return a < b; }

    PriorityQueue<i32> pq = PriorityQueue<i32>::new(lessI32);
    pq.push(5);
    pq.push(1);
    pq.push(3);
    i32 min = pq.pop();            // 1
    i32 peeked = pq.peek();        // the next one out, without removing

The comparator is `bool(T, T) less` — "is a strictly before b?" — the same shape Vec's `sortBy` uses. To make a max-heap, hand it `bool greaterI32(i32 a, i32 b) { return a > b; }`. A priority queue is the engine of Dijkstra's algorithm, of event-driven simulation, and of scheduling; we use it for ranking in the worked example below.

16.8 LinkedList<T>

A linked list is a chain of nodes, each pointing at the next. It is the structure to reach for sparingly — an array beats it for almost every access pattern because of cache locality — but it is unbeatable when you need O(1) insertion and removal given a cursor, and it expresses an intrusive pointer-linked structure directly.

    import(lib) std::collections.linkedlist { LinkedList };

    LinkedList<i32> l = LinkedList<i32>::new();
    l.pushBack(1);
    l.pushBack(2);
    l.pushFront(0);

    i32 head = l.front();
    i32 tail = l.back();
    i32 popF = l.popFront();
    i32 popB = l.popBack();
    l.each(printI32);

The library provides it because some interfaces and some designs genuinely want it; it does not present it as the default list. The default list is Vec.

16.9 Tree and Trie

Two specialised structures round out the collection family.

`Tree<T>` is a general tree — a node with children — the shape of a file system, a scene graph, an abstract syntax tree, an organisational chart. Its nodes hold a value and a vector of child pointers:

    pub struct TreeNode<T> {
        T value;
        Vec<TreeNode<T>*> children;
    }

    pub struct Tree<T> {
        TreeNode<T>* root;
    }

    import(lib) std::collections.tree { Tree };

    Tree<str> root = Tree<str>::new();
    TreeNode<str>* r = root.setRoot("root");
    TreeNode<str>* docs = root.addChild(r, "docs");
    TreeNode<str>* src  = root.addChild(r, "src");

    usize kids = root.childCount(r);
    Option<TreeNode<str>*> first = root.childAt(r, 0);
    root.preOrder(printNodeValue);     // depth-first, parent first
    root.postOrder(printNodeValue);    // depth-first, children first
    usize d = root.depth(r);
    usize total = root.size();
    Vec<str> flat = root.toVec();

Because a Tree is not a Vec, iteration is through `preOrder` and `postOrder`, which take a `void(T)` function.

`Trie` is the prefix tree, keyed on the bytes of a string. It is ideal for autocomplete, spell-check dictionaries, and routing tables, where the query is "all keys with this prefix":

    import(lib) std::collections.trie { Trie };

    Trie dict = Trie::new();
    dict.insert("car");
    dict.insert("cart");
    dict.insert("cat");

    if (dict.contains("car")) { ... }
    if (dict.startsWith("ca")) { ... }
    bool removed = dict.remove("cart");
    dict.each(printWord);

Note what the trie stores: it is a set of keys, not an associative map, so `insert` takes only the key. If you need a payload per word, use the key to look the payload up in a companion Map.

16.10 Bitset and Cache

`Bitset` is a fixed-width set of bits packed into 64-bit words. It is the right structure for a dense set of small non-negative integers — a set of visited nodes in a graph, an array of feature flags — where a `Set<usize>` would spend sixty-four bits storing what one bit could hold.

    import(lib) std::collections.bitset { Bitset };

    Bitset visited = Bitset::new(256);
    visited.set(42);
    visited.toggle(7);
    if (visited.test(42)) { ... }
    visited.clear(42);

    u64 setBits   = visited.countOnes();
    u64 clearBits = visited.countZeros();
    bool any      = visited.hasAny();
    bool allSet   = visited.all();

Bitsets also do bitwise algebra in place, which is how they earn their keep in algorithms that operate on sets of nodes:

    visited.and(&other);
    visited.or(&other);
    visited.xor(&other);
    visited.not();
    visited.setAll();
    visited.clearAll();

`Cache<K, V>` is a bounded, eviction-aware map — the standard tool when a map must not grow without limit. Right now the eviction policy is a true LRU: on every hit the entry is moved to the most-recently-used end, and when the cache is full the coldest entry is dropped. Because it also needs a hash and an equality for keys, the constructor takes all three:

    import(lib) std::collections.cache { Cache };

    Cache<str, Page> pages = Cache<str, Page>::new(128, hashStr, eqStr);

    pages.insert(url, fetch(url));      // may evict the coldest
    Option<Page> hot = pages.get(url);  // a hit moves it to the hot end
    Option<Page*> p  = pages.getPtr(url);
    bool here = pages.contains(url);
    pages.remove(url);
    pages.each(visitPage);
    pages.resize(256);

Having an LRU cache in the standard library means you do not rebuild it, subtly differently, in every project. We use it in the second worked example.

16.11 iter and sort

Two utilities cut across every container.

`std::collections::sort` implements the ordering algorithms on Vecs, with typed entry points for the common element types and a generic one for the rest:

    import(lib) std::collections::sort {
        sortI32, sortF64, sortusize,
        sortBy, isSortedI32, binarySearchI32,
        binarySearchBy, reverse
    };

    Vec<i32> v = Vec<i32>::new();
    v.push(3); v.push(1); v.push(2);
    sortI32(&v);                            // ascending

    bool ordered = isSortedI32(&v);
    isize idx = binarySearchI32(&v, 2);     // index, or -1

For any other element type, `sortBy` takes the "less than" predicate, and `binarySearchBy` takes the three-way comparator:

    sortBy(&v, lessSomeType);
    isize where = binarySearchBy(&v, key, cmpSomeType);

`std::collections.iter` provides the adaptors that make bulk operations read as transformations rather than loops. Each takes a pointer to a Vec and a function, and each returns a new Vec or a folded value:

    import(lib) std::collections::iter {
        map, filter, reduce, forEach, find, findIndex,
        hasAny, all, take, skip, slice, zip,
        countIf, minBy, maxBy, unique, flatten,
        enumerate, sum, average
    };

    Vec<i32> doubled = map(&v, double);
    Vec<i32> evens   = filter(&v, isEven);
    i32 total        = reduce(&v, 0, add);
    i32 biggest      = maxBy(&v, lessI32);
    usize howMany    = countIf(&v, isEven);
    Vec<i32> firstTwo = take(&v, 2);
    Vec<i32> rest     = skip(&v, 2);
    Vec<usize> indices = enumerate(&v);
    i32 s            = sum(&v);
    f64 avg          = average(&f64v);

The pipeline reads in the order the operations happen, which is the property a loop with a temporary variable loses. Note the names precisely: the folder is `reduce`, not `fold`; the typed sorts are `sortI32` and friends rather than a bare `sort`; and every adaptor wants a pointer, so you call `map(&v, f)` and not `map(v, f)`.

16.12 Ownership: Who Frees What

Every container in this chapter owns its elements, and freeing a container frees what it owns. The rules are the RAII rules of Chapter 11, specialised:

    - A Vec<T> owns its backing array and its elements. Dropping it frees
      the array and drops each element whose type has a drop.
    - A Map<K, V>, HashMap<K, V>, or Cache<K, V> owns its keys and values.
    - A Bitset owns one heap array of words and frees it on dispose.
    - An Arr<T, N> owns inline storage; there is nothing to free.
    - A container of pointers owns the pointers, not their targets. The
      target's lifetime is a separate question the type must answer.

That last rule is where bugs live. A `Vec<T*>` whose element type is a bare pointer frees the array but not the pointees; if the program allocated them, it must free them, and the cleanest way to say so is to use a smart-pointer element type — `SmartPtr<T>` or `SharedPtr<T>` from `std::memory` — so that the container's drop cascades into the elements' drop. A container of owning smart pointers is self-managing; a container of raw pointers is a footgun with a clear label.

When a container must be shared between parts of a program, `SharedPtr<T>` reference-counts it so the last reference to go away frees it. When a container needs a custom allocation strategy — an arena for a parse tree, a pool for fixed-size nodes — the `std::memory` module supplies `Allocator`, `Pool<T>`, `ArenaAllocator`, `PoolAllocator`, and the fixed-buffer and scope allocators. The standard containers are built on the same allocation primitives the language exposes, so a program that needs a different strategy supplies the allocator rather than being locked out of the containers. Chapter 11 and Appendix A go into those.

16.13 A Worked Example: Word Frequency

Put the collections to work on a task that needs several at once: count how often each word appears in a text and print the ten most frequent. Three containers cooperate — a hashed map to count, its key list to fan out, and a priority queue to rank.

    import(lib) std::io::ios { println, readLine };
    import(lib) std::text::strutil { splitVec, trim };
    import(lib) std::text::ascii { toAsciiLower };
    import(lib) std::collections.hashmap { HashMap };
    import(lib) std::collections.priorityqueue { PriorityQueue };
    import(lib) std::text::string { String };

    usize hashStr(str k) {
        usize h = 5381;
        for (usize i = 0; i < k.len; i += 1) h = h * 33 + (usize)k.ptr[i];
        return h;
    }
    bool eqStr(str a, str b) { return a.equals(b); }

    struct WordCount {
        str word;
        i32 count;
    }

    bool moreFrequent(WordCount a, WordCount b) {
        return a.count > b.count;          // most frequent comes out first
    }

    i32 main() {
        HashMap<str, i32> counts = HashMap<str, i32>::new(hashStr, eqStr);

        String line = String::new();
        while (readLine(&line)) {
            if (line.isEmpty()) break;
            for (str raw : splitVec(line.asView(), ' ')) {
                str word = trim(raw);
                if (word.len == 0) continue;
                Option<i32> seen = counts.get(word);
                i32 next = seen.isSome() ? seen.unwrap() + 1 : 1;
                counts.insert(word, next);
            }
        }

        PriorityQueue<WordCount> top = PriorityQueue<WordCount>::new(moreFrequent);
        for (str word : counts.keys()) {
            top.push(WordCount { .word = word, .count = counts.get(word).unwrap() });
        }

        for (i32 i = 0; i < 10 && !top.isEmpty(); i += 1) {
            WordCount wc = top.pop();
            println("{}: {}", wc.word, wc.count);
        }
        return 0;
    }

Four moving parts, each doing what it is for. The HashMap accumulates counts by key. Its `keys` method produces a Vec of the distinct words to fan out over. The PriorityQueue orders them by a comparator so the top ten are simply the first ten pops. A small struct packages the pair. No container does another's job, and the whole program is a page. That is the shape a good standard library enables: the data structures are right, so the algorithm is short.

16.14 A Worked Example: An LRU Page Cache

The second example uses the Cache container for the task it exists for, then shows what it would cost to build by hand.

    import(lib) std::collections.cache { Cache };
    import(lib) std::text::string { String };

    usize hashStr(str k) { ... }        // as above
    bool eqStr(str a, str b) { return a.equals(b); }

    struct Page { String contents; }

    Cache<str, Page> pages = Cache<str, Page>::new(256, hashStr, eqStr);

    Page* fetchPage(str url) {
        Option<Page*> hot = pages.getPtr(url);
        if (hot.isSome()) {
            return hot.unwrap();        // touched; stays hot
        }
        Page fresh = loadFromNetwork(url);
        pages.insert(url, fresh);       // may evict the coldest
        return pages.getPtr(url).unwrap();
    }

The eviction policy is the container's business: `insert` adds an entry and, if the cache is full, removes the least-recently-used one; `get` and `getPtr` move a hit to the hot end so a frequently used page survives. A hand-rolled version of this is thirty lines of doubly-linked-list-plus-map bookkeeping, with a classic bug — forgetting to move an element on a get — that shows up only under load. The library's version has that bug fixed once. Using it is not just less code; it is the difference between a cache that is correct and a cache that is almost correct.

16.15 Exercises

1. Comprehension. You need to look up values by string key and iterate in sorted order. Which map type do you choose, and what extra thing must you supply that a HashMap does not need? Could you use HashMap and sort the keys yourself? What does each approach cost?

2. Comprehension. Why does Vec expose `data`, `len`, and `cap` as public fields rather than hiding them? Give one advantage and one risk this creates.

3. Implementation. Write a function that, given a `Vec<i32>`, returns a new `Vec<i32>` containing each element doubled and the zeros removed. Use the `iter` adaptors `map` and `filter`, then rewrite it with an explicit loop and compare the two.

4. Containers. Build an LRU cache by hand using a `HashMap` and a `LinkedList`. Then replace it with `Cache`. How many lines does each version take, and which operations were easy to get wrong?

5. Signatures. `Map::new`, `HashMap::new`, `Set::new`, and `Cache::new` all take functions. Write the exact parameter lists of each from memory, then check them against Appendix A. Why does the ordered map take a single `i32(K, K)` while the hashed ones take a `usize(K)` and a `bool(K, K)`?

6. Ownership. Declare a `Vec<T*>` of pointers you allocated. Free the Vec and then try to free each pointee. What is the correct order? What happens if you free the pointees first? Rewrite it with `SmartPtr<T>` elements and say what disappears.

7. Sets. Given two `Vec<str>` of names, compute their intersection as a `Set<str>`. What is the running time of your approach, and why is it better than the nested-loop version? Then do the same with `Set::difference`.

8. Priority. Modify the word-frequency program to print the ten least frequent words instead of the most frequent. What changes, and what does not? Watch the comparator carefully.

9. Between. A circular buffer of audio samples is written fast and read slower than it is written, and it must never allocate. Which container do you use, and why not Deque? What happens to the oldest samples when it fills?

10. Bitset. Represent the adjacency of a graph with 512 nodes as a `Bitset`. How much storage does this save versus a `Set<usize>` or a `Vec<bool>`? Then use `and`, `or`, and `countOnes` to count the common neighbours of two nodes.

11. Trie. Build a `Trie` of a few hundred words. Write a function that, given a prefix, returns how many stored words have it. (Hint: `startsWith` tells you presence; to count, you may need a `Vec<str>` and an `each` pass.)

12. Meta. The library offers Map, HashMap, and UnorderedMap, and separately Queue, Deque, and RingBuf. Argue for and against this proliferation of types. Where is the line between a useful distinction and a choice the programmer should make once?
