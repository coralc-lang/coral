Chapter 34

Live Examples: Systems and Concurrency

The Machinery You Can See

Chapter 18 told the story of concurrency: what a thread is, why a data race is undefined behaviour, what happens-before means, and how a mutex and a condition variable turn a collection of independently running threads into a correct exchange. This chapter is the workshop. It takes those primitives and builds the six structures that every real system is assembled from: a race that a counter loses, a producer and a consumer passing work across a queue, a thread pool draining a task list, a parallel map over a vector, an async pipeline that suspends and resumes, and a semaphore that caps how many things happen at once. Each one is short. Each one is a pattern you will meet again, often under a different name.

The promise of this chapter is that the machinery is visible. Coral does not hide the thread behind a keyword, the queue behind a runtime, or the scheduler behind magic. `threadCreate` returns a real operating system thread and a `Result` that says whether it worked. A mutex is a struct you `init` and `lock`. A condition variable is a nap with an alarm. When you read a function in this chapter, you can point at the exact line that establishes the happens-before edge, and that is the point: correctness in concurrent code is not a property you hope for, it is a property you can audit, lock by lock and signal by signal.

Two habits carry through every example, and they are worth naming before the first one. First: every piece of shared mutable state is touched only while holding the lock that protects it, and the function is written so that a reviewer can see that in one reading. Second, and this is the one beginners skip: every wait on a condition variable happens inside a `while` loop that rechecks the predicate. The platform is allowed to wake a waiter for its own reasons, and another thread may have taken what you waited for; the loop is not defensive style, it is part of the protocol.

A last word on the shape of a thread's argument. Every thread in Coral runs a function that takes one `rawptr` and returns one `rawptr` (a pool task returns `void`). That single pointer must carry everything the worker needs, so in practice it points at a struct. The pointer is where the lifetime contract begins: if it points at a local that dies before the join, you have a use-after-free the compiler cannot see. Every example below either points at data that outlives the join, or allocates its job and frees it when the task is done.

34.1 The Lost Update: Why a Counter Needs an Atomic

The problem. Two threads each add one to a shared counter a million times. The answer should be two million. Write the obvious code and it is almost always less, and the shortfall changes on every run.

The intuition. The line `count += 1` is not one action; it is three. The processor loads the current value into a register, adds one, and stores it back. When two threads do this at the same instant — both load seven, both compute eight, both store eight — one increment is lost. The operations interleaved by pure timing, and nothing in the program ordered them. This is a data race, and its result is not a stable wrong answer but an unpredictable one. The fix is a single-word atomic: an operation the hardware guarantees no other thread can observe half-done. `AtomicU64` loads, stores, and does read-modify-write in one indivisible step.

The approach. Write the broken version first, deliberately, because the failure is the lesson and because it never reproduces on demand. Then replace the plain `u64` with an `AtomicU64` and watch the count come out exact every time.

The implementation.

    import(lib) std::concurrent::thread {
        threadCreate, threadJoin, Thread, ThreadError, AtomicU64
    };

    struct PlainCounter { u64 value; }
    struct AtomicCounter { AtomicU64 value; }

    rawptr bumpPlain(rawptr arg) {
        PlainCounter* c = (PlainCounter*)arg;
        for (u64 i = 0; i < 1000000u; i += 1) c->value += 1;
        return null;
    }

    rawptr bumpAtomic(rawptr arg) {
        AtomicCounter* c = (AtomicCounter*)arg;
        for (u64 i = 0; i < 1000000u; i += 1) c->value.fetchAdd(1u);
        return null;
    }

    pub i32 main() {
        PlainCounter plain = PlainCounter { .value = 0 };
        Result<Thread, ThreadError> a = threadCreate(bumpPlain, (rawptr)&plain);
        Result<Thread, ThreadError> b = threadCreate(bumpPlain, (rawptr)&plain);
        if (a.isOk()) threadJoin(a.unwrap(), null);
        if (b.isOk()) threadJoin(b.unwrap(), null);
        println("plain  {}", plain.value);          // often less than 2000000

        AtomicCounter atomic = AtomicCounter { .value = AtomicU64 { .value = 0 } };
        Result<Thread, ThreadError> c = threadCreate(bumpAtomic, (rawptr)&atomic);
        Result<Thread, ThreadError> d = threadCreate(bumpAtomic, (rawptr)&atomic);
        if (c.isOk()) threadJoin(c.unwrap(), null);
        if (d.isOk()) threadJoin(d.unwrap(), null);
        println("atomic {}", atomic.value.load());  // always 2000000
        return 0;
    }

Cost and notes. `fetchAdd` is a single locked instruction on x86-64 (`lock xadd`), a few tens of cycles, saturated and indivisible. The plain increment is faster in isolation and wrong. The rule of thumb from Chapter 18 is exact: use an atomic when the shared state is one integer — a counter, a flag, a ticket — and use a mutex the moment the state is anything larger. An atomic guards one cell; a mutex guards a region.

Edge cases. The plain version is a genuine data race and its result is undefined, not merely imprecise; it may occasionally print two million on a fast machine with light contention, which is exactly why it is dangerous. The two threads must write through the same pointer, so the counter's lifetime must exceed both joins. `load`, `store`, `fetchAdd`, `fetchSub`, and `compareExchange` are the whole vocabulary, and each is a hardware guarantee rather than a simulation. And `AtomicU64 { .value = 0 }` is the initialisation; forgetting it leaves the counter holding whatever was on the stack.

Variation. Two threads incrementing and one decrementing, with the result printed after all three join. The expected total is one million regardless of interleaving; confirm that the atomic version always reaches it and the plain version does not. Then try `compareExchange` to build a lock-free "increment only if below a cap" and explain the retry loop.

34.2 Producer and Consumer with a Mutex and a Condition Variable

The problem. One thread produces values; another consumes them; they must meet in the middle without the producer overrunning a fixed-size buffer and without the consumer spinning on an empty one.

The intuition. This is the single most reusable structure in concurrent programming. A thread pool is this queue with tasks. A channel is this queue with a protocol. An actor's mailbox is this queue. It is a fixed-size ring of slots, a mutex, and two condition variables: one that says "an item is ready" and one that says "room is free." The producer locks, waits while the ring is full, writes, signals that an item is ready, and unlocks. The consumer locks, waits while the ring is empty, reads, signals that room is free, and unlocks. The two signals cross: each side wakes the other precisely when the other can make progress.

The approach. A ring buffer with `head` and `count`, protected by one mutex, with two condition variables. A `closed` flag lets the consumer drain and stop. The waits are all inside `while` loops, for the three named reasons (lost wakeup, spurious wakeup, stale predicate).

The implementation.

    import(lib) std::concurrent::mutex { Mutex };
    import(lib) std::concurrent::thread {
        ConditionVar, threadCreate, threadJoin, Thread, ThreadError
    };
    import(lib) std::mman { alloc, dealloc };

    pub struct Queue {
        Mutex mutex;
        ConditionVar itemReady;
        ConditionVar roomFree;
        u64* items;
        usize cap;
        usize head;
        usize count;
        bool closed;

        bool init(usize capacity) {
            self.items = alloc<u64>(capacity);
            if (self.items == null) return false;
            self.mutex.init();
            self.itemReady.init();
            self.roomFree.init();
            self.cap = capacity;
            self.head = 0;
            self.count = 0;
            self.closed = false;
            return true;
        }

        void destroy() {
            self.mutex.destroy();
            self.itemReady.destroy();
            self.roomFree.destroy();
            dealloc<u64>(self.items);
        }

        void push(u64 value) {
            self.mutex.lock();
            while (self.count == self.cap && !self.closed)
                self.roomFree.wait(&self.mutex);
            if (self.closed) { self.mutex.unlock(); return; }

            self.items[(self.head + self.count) % self.cap] = value;
            self.count += 1;
            self.itemReady.signal();
            self.mutex.unlock();
        }

        bool pop(u64* out) {
            self.mutex.lock();
            while (self.count == 0 && !self.closed)
                self.itemReady.wait(&self.mutex);
            if (self.count == 0) { self.mutex.unlock(); return false; }

            *out = self.items[self.head];
            self.head = (self.head + 1) % self.cap;
            self.count -= 1;
            self.roomFree.signal();
            self.mutex.unlock();
            return true;
        }

        void close() {
            self.mutex.lock();
            self.closed = true;
            self.itemReady.broadcast();
            self.roomFree.broadcast();
            self.mutex.unlock();
        }
    }

    rawptr producer(rawptr arg) {
        Queue* q = (Queue*)arg;
        for (u64 i = 1; i <= 100; i += 1) q->push(i);
        q->close();
        return null;
    }

    rawptr consumer(rawptr arg) {
        Queue* q = (Queue*)arg;
        u64 value;
        u64 sum = 0;
        while (q->pop(&value)) sum += value;
        println("sum {}", sum);
        return null;
    }

    pub i32 main() {
        Queue q;
        if (!q.init(16)) return 1;
        Result<Thread, ThreadError> p = threadCreate(producer, (rawptr)&q);
        Result<Thread, ThreadError> c = threadCreate(consumer, (rawptr)&q);
        if (p.isOk()) threadJoin(p.unwrap(), null);
        if (c.isOk()) threadJoin(c.unwrap(), null);
        q.destroy();
        return 0;
    }

The sum prints 5050 — the sum of one through a hundred — every time, though the interleaving of the two threads differs on every run. The ring arithmetic `(head + count) % cap` is the entire buffer discipline: `head` is the oldest slot, `count` is how many are live, and the modulo keeps the indices in range without ever moving a value. The `close` broadcast, called the poison pill, wakes both waiters so the consumer's loop ends on `false` and no thread is left asleep forever.

Cost and notes. Each push and pop takes one lock, one or two signals, and O(1) bookkeeping. The mutex is held only for the bookkeeping and is released before any work is done on the item, so the critical section is tiny. The backpressure is the point: a fast producer blocks when the buffer is full instead of the memory growing until the machine dies, and that blocking is what keeps the two sides in step.

Edge cases. The buffer must never be touched outside the locked region; a single unlocked read of `count` reintroduces the race. Both waits recheck after waking, because `signal` wakes one waiter but the woken thread may find the predicate false. `close` uses `broadcast`, not `signal`, because every waiter must see the closure. And a producer that closes while the consumer is mid-`pop` is fine, because `pop` rechecks `count` after the wake and returns what is left before returning false.

Variation. Generalise the element type to `rawptr` so the queue carries pointers to arbitrary jobs, which is exactly what the next example's thread pool does. Then add a second consumer thread and confirm the sum is still 5050 — the correctness does not depend on how many consumers there are, only on the lock discipline.

34.3 A Thread-Pool Task Queue

The problem. `threadCreate` per task does not scale: the operating system charges for a kernel object, a stack, and a scheduler slot, and a program that spawns a thread per request spends its life in the kernel. A pool creates a fixed set of workers once and feeds them tasks from a queue.

The intuition. A pool is the producer–consumer queue of 34.2, with the tasks as items, the workers as consumers, and a stop flag for shutdown. The producer is any thread that calls `submit`; the consumers are the workers, each running the same loop: lock, wait for a task or a stop, take one, unlock, run it, repeat. The queue is a linked list because tasks arrive and leave one at a time and a list needs no fixed capacity. The stop flag has its own discipline: on shutdown, set it under the lock and broadcast, so a sleeping worker wakes, rechecks, and exits after draining what is queued.

The approach. A compact pool built directly on `Mutex`, `ConditionVar`, and `threadCreate`. `std::concurrent::threadpool::ThreadPool` is the production version of exactly this structure; reading its source after writing this one is the best way to see that there is no hidden machinery.

The implementation.

    import(lib) std::concurrent::mutex { Mutex };
    import(lib) std::concurrent::thread {
        ConditionVar, threadCreate, threadJoin, Thread, ThreadError
    };
    import(lib) std::mman { alloc, dealloc };

    struct Task {
        void(rawptr) work;
        rawptr arg;
        Task* next;
    }

    pub struct MiniPool {
        Mutex mutex;
        ConditionVar cond;
        Thread* workers;
        Task* head;
        Task* tail;
        u32 nthreads;
        bool stop;

        bool init(u32 numThreads) {
            if (numThreads == 0) return false;
            self.mutex.init();
            self.cond.init();
            self.head = null;
            self.tail = null;
            self.stop = false;
            self.nthreads = numThreads;
            self.workers = alloc<Thread>((usize)numThreads);
            if (self.workers == null) return false;
            for (u32 i = 0; i < numThreads; i += 1) {
                Result<Thread, ThreadError> r = threadCreate(miniEntry, (rawptr)self);
                if (r.isErr()) { self.shutdown(); return false; }
                self.workers[i] = r.unwrap();
            }
            return true;
        }

        bool submit(void(rawptr) work, rawptr arg) {
            if (work == null) return false;
            Task* t = alloc<Task>(1);
            if (t == null) return false;
            t->work = work;
            t->arg = arg;
            t->next = null;

            self.mutex.lock();
            if (self.stop) { self.mutex.unlock(); dealloc<Task>(t); return false; }
            if (self.tail != null) self.tail->next = t;
            else self.head = t;
            self.tail = t;
            self.mutex.unlock();
            self.cond.signal();
            return true;
        }

        void workerLoop() {
            loop {
                self.mutex.lock();
                while (self.head == null && !self.stop) self.cond.wait(&self.mutex);
                if (self.stop && self.head == null) { self.mutex.unlock(); return; }

                Task* t = self.head;
                self.head = t->next;
                if (self.head == null) self.tail = null;
                self.mutex.unlock();

                t->work(t->arg);
                dealloc<Task>(t);
            }
        }

        void shutdown() {
            self.mutex.lock();
            self.stop = true;
            self.mutex.unlock();
            self.cond.broadcast();
            for (u32 i = 0; i < self.nthreads; i += 1) threadJoin(self.workers[i], null);
            self.mutex.lock();
            while (self.head != null) {
                Task* t = self.head;
                self.head = t->next;
                dealloc<Task>(t);
            }
            self.mutex.unlock();
            self.workers = null;
            self.mutex.destroy();
            self.cond.destroy();
        }
    }

    rawptr miniEntry(rawptr arg) {
        ((MiniPool*)arg)->workerLoop();
        return null;
    }

Cost and notes. Submission is O(1): allocate a task, link it under the lock, signal. A worker's idle cost is zero — it sleeps on the condition variable and consumes nothing until signalled. The concurrency is bounded by the number of workers, which is a tuning decision: one per core for CPU-bound work, more for tasks that block on I/O, fewer when tasks contend for a shared lock. The pool replaces one thread creation per task with one per worker, and turns the per-task cost into a queue push.

Edge cases. The stop path must both set the flag under the lock and broadcast after releasing it, so a worker that checked the empty queue and was about to wait does not miss the wake; the standard order is set-and-unlock, then broadcast. A task submitted just before shutdown is either run or freed, never stranded; `shutdown` drains the list after all workers have stopped. If thread creation fails partway, `shutdown` joins the workers already made and returns failure. And `submit` returns `false` rather than silently dropping a task if the pool is stopping.

Variation. Add a `pending()` method that returns the number of queued tasks under the lock, and use it to build a `drain()` that blocks until the queue is empty. It is the missing piece for a batch program that submits a thousand jobs and then waits for all of them, and it demonstrates that the pool's state is fully visible through the mutex.

34.4 Parallel Map over a Vec

The problem. Apply a function to every element of a large vector, using every core. This is the simplest and most common parallel pattern, and it is the one a data-processing pipeline reaches for first.

The intuition. Split the vector into contiguous chunks, hand each chunk to a task, and let the pool run the tasks at once. Each task writes only to its own slice of the output, so the threads never touch the same memory and no lock is needed for the data itself; the only shared thing is the output buffer, and each task owns a disjoint region of it. The chunk boundaries are the coordination. Then wait for the pool to drain, and the whole vector is mapped. This is the cleanest possible demonstration that parallelism is a resource problem: the work is divided, the resources are used, and nothing is shared that does not have to be.

The approach. Use the standard `ThreadPool`. Define a job that carries a pointer to the input, a pointer to the output, a range, and the function to apply. Allocate an array of jobs, submit each, then `deinit` — which drains all queued work before the workers exit. Because the input and output outlive the pool and each job writes a disjoint range, no additional synchronisation is needed.

The implementation.

    import(lib) std::concurrent::threadpool { ThreadPool };
    import(lib) std::vec { Vec };
    import(lib) std::mman { alloc, dealloc };

    struct MapJob {
        const Vec<f64>* input;
        Vec<f64>* output;
        usize start;
        usize end;
        f64(f64) func;
    }

    void runMapChunk(rawptr arg) {
        MapJob* job = (MapJob*)arg;
        for (usize i = job->start; i < job->end; i += 1)
            job->output->set(i, job->func(job->input->at(i)));
    }

    pub f64 square(f64 x) { return x * x; }

    pub bool parallelMap(const Vec<f64>* input, Vec<f64>* output, f64(f64) func, u32 workers) {
        usize n = input->count();
        output->clear();
        for (usize i = 0; i < n; i += 1) output->push(0.0);   // reserve the slots

        usize chunks = (usize)workers;
        if (chunks > n) chunks = n;
        if (chunks == 0) return true;

        MapJob* jobs = alloc<MapJob>(chunks);
        if (jobs == null) return false;

        ThreadPool pool;
        if (!pool.init(workers)) { dealloc<MapJob>(jobs); return false; }

        usize per = n / chunks;
        usize extra = n % chunks;
        usize start = 0;
        for (usize c = 0; c < chunks; c += 1) {
            usize len = per + (c < extra ? 1 : 0);
            jobs[c] = MapJob {
                .input = input,
                .output = output,
                .start = start,
                .end = start + len,
                .func = func
            };
            pool.enqueue(runMapChunk, (rawptr)&jobs[c]);
            start += len;
        }

        pool.deinit();        // drains every queued task, then joins the workers
        dealloc<MapJob>(jobs);
        return true;
    }

The chunking gives the first `extra` chunks one element more than the rest, so the pieces cover the vector exactly even when the length is not a multiple of the worker count. A fire-and-forget version that did not call `deinit` would return while the workers were still writing, and the caller would read a half-mapped vector; `deinit`'s drain-then-join is what makes the return value meaningful.

Cost and notes. The wall-clock time should approach the single-threaded time divided by the number of workers, up to the overhead of submission and the fact that some workers finish before others. The overhead is real: each task carries a struct and a queue push, and for tiny vectors the parallel version is slower than a plain loop. Parallelism pays when each chunk is large enough to dwarf the coordination, which is why the chunk count is a parameter and not a constant.

Edge cases. The output vector must already have `n` slots before the tasks run, because `set` writes into existing positions and `at` would be out of range otherwise; the pre-fill loop is the allocation. Each job's range must be disjoint from every other's, or two threads write the same cell and the result is a race; the `start`/`len` arithmetic guarantees it. The function passed must be safe to run on many threads at once, which rules out anything that mutates shared state. And the jobs array and the pool must both be cleaned up on the failure paths, which the early returns do.

Variation. Replace the map with a parallel reduction: instead of writing each result, each chunk computes a partial sum and the caller combines the partials. The partials must be written to distinct slots (one per chunk) and combined afterward, because summing into one shared accumulator would need an atomic or a lock. Doing it both ways shows how the pattern changes when the threads must combine rather than partition.

34.5 An Async Pipeline with spawn, await, and a Channel

The problem. Coordinate several I/O-shaped stages — fetch, transform, store — so that while one stage waits, the others progress, without dedicating an operating-system thread to each wait.

The intuition. A thread that sleeps blocks a thread; an async task that sleeps frees its execution context for other work. Coral's async runtime is a set of lightweight stacks called fibers, driven by whoever calls `run`. `spawn(fn, arg)` puts a function on its own fiber and returns a `Future*` — a one-shot result cell. `await(future)` suspends the calling fiber until the future is ready, then returns its result. `sleep(ms)` returns a future that resolves later, and awaiting it suspends the fiber for that long without blocking a thread. The top level of the program is not a fiber, so it cannot await; instead it spawns a coordinator and calls `run` to drive the scheduler to completion. The rule is: await inside a fiber, drive from outside.

The approach. A producer fiber pushes values into an `AsyncChannel` with a sleep between them to model latency; a consumer fiber receives and accumulates them. The top level spawns both and runs the scheduler.

The implementation.

    import(lib) std::concurrent::async;
    import(lib) std::io::ios { println };

    pub void producerStage(rawptr arg) {
        async::AsyncChannel* ch = (async::AsyncChannel*)arg;
        for (u64 i = 1; i <= 5; i += 1) {
            async::await(async::sleep(10));       // pretend to do I/O
            ch->send((rawptr)i);
        }
    }

    pub void consumerStage(rawptr arg) {
        async::AsyncChannel* ch = (async::AsyncChannel*)arg;
        u64 total = 0;
        for (u64 i = 0; i < 5; i += 1) {
            Result<rawptr, async::AsyncError> got = async::await(ch->recv());
            if (got.isOk()) total += (u64)got.unwrap();
        }
        println("async total {}", total);
    }

    pub i32 main() {
        async::init();
        async::AsyncChannel ch;
        if (!ch.init(4)) return 1;

        Result<async::Future*, async::AsyncError> p = async::spawn(producerStage, (rawptr)&ch);
        Result<async::Future*, async::AsyncError> c = async::spawn(consumerStage, (rawptr)&ch);
        if (p.isErr() || c.isErr()) return 1;

        async::run();     // drive until every spawned fiber has finished
        ch.deinit();
        return 0;
    }

The producer sleeps, then sends; the consumer awaits a receive and adds what arrives. The `send((rawptr)i)` casts the integer to the channel's raw-pointer element type, and the consumer casts it back with `(u64)got.unwrap()`. The channel is buffered with capacity four, so sends and receives do not have to meet exactly; a zero capacity would make it a rendezvous, where a send succeeds only against an already-parked receiver.

Cost and notes. The run-time cost of a fiber switch is a stack swap, cheaper than a kernel context switch, and the stacks are heap blocks recycled as fibers finish. The `sleep` is wall-clock and does not consume a thread; the scheduler idles in a timed wait on the same clock and wakes when the next timer is due. The gain over threads appears when many tasks spend most of their lives waiting, which is the I/O-bound case: one driver thread can hold thousands of suspended fibers on a fraction of the memory that many threads would need.

Edge cases. Calling `await` outside a fiber reports that plainly and returns an error, because there is nowhere to suspend to; this is why the top level spawns and drives rather than awaiting directly. A future can be awaited by someone who never receives a value if no send ever matches it; v1 futures are not individually cancellable, and a pending receive that nobody sends to can stall the scheduler. And a blocking call inside a fiber stalls the whole runtime on that thread, which is the one discipline async demands: never block inside a task.

Variation. Add a second consumer and a second channel, and route values to them in round-robin. It is the skeleton of a worker pipeline, and it shows that a channel per stage is the natural way to express the connections between them.

34.6 Bounding Concurrency with a Semaphore

The problem. You have a hundred tasks and only four database connections. Every task wants a connection, and if they all grab one the database falls over. You need at most four tasks inside the connection-using region at once, regardless of how many tasks exist.

The intuition. A mutex lets one through; a semaphore lets a fixed number through. It holds a count, `wait` decrements and blocks at zero, and `post` increments and wakes a waiter. Initialise it to four and exactly four tasks proceed; the rest queue on the wait without spinning. The semaphore has no owner — any thread may `post`, and it may release another thread's `wait` — which is the difference between it and a mutex, and the reason it can also serve as a signal.

The approach. A shared counter of tasks that have finished, a semaphore of four permits, and a worker function that waits for a permit, does its work, and posts it back. The pool of tasks is larger than the permits on purpose.

The implementation.

    import(lib) std::concurrent::semaphore { Semaphore };
    import(lib) std::concurrent::thread {
        threadCreate, threadJoin, Thread, ThreadError
    };

    struct Gate {
        Semaphore permits;
        u64* completed;
    }

    rawptr limitedTask(rawptr arg) {
        Gate* gate = (Gate*)arg;
        gate->permits.wait();
        // only four threads are ever inside this region at once
        *gate->completed += 1;        // caller guarantees this is the only writer
        gate->permits.post();
        return null;
    }

    pub void runLimited(u32 maxConcurrent, u32 taskCount) {
        Gate gate;
        if (!gate.permits.init(maxConcurrent)) return;
        u64 completed = 0;
        gate.completed = &completed;

        // in a real program the tasks come from the pool; here they run directly
        Thread* threads = null;       // placeholder for a pool in production
        for (u32 i = 0; i < taskCount; i += 1) {
            Result<Thread, ThreadError> t = threadCreate(limitedTask, (rawptr)&gate);
            if (t.isOk()) threadJoin(t.unwrap(), null);
        }
        gate.permits.destroy();
        println("completed {}", completed);
    }

The example above creates and joins a thread per task for clarity; in production the tasks would be submitted to the pool from 34.3, and the semaphore would cap how many ran the guarded section at once. The essential lines are the three around the critical work: `wait`, do, `post`. Everything between the wait and the post runs under the cap, no matter how many tasks exist.

Cost and notes. `wait` and `post` are cheap kernel operations, far cheaper than creating a thread, and the queue of blocked waiters is handled by the kernel without spinning. The semaphore's promise is a maximum, unchanged by what happens inside: "never more than four connections open, whatever the work does" — provided the work cannot throw a path that skips the post, which is why RAII or a single-exit structure matters. A binary semaphore, initialised to one, is almost a mutex, but its lack of ownership means any thread can release it; use the mutex to own a region and the semaphore to limit and to signal.

Edge cases. A `post` without a matching `wait` raises the count above its initial value and lets more than the intended number through, so every `wait` must be paired with exactly one `post` on every path. Initialising to zero makes a pure signal, where a producer posts and a consumer waits. The shared counter in this example is safe only because the tasks are joined one at a time; with real parallelism it would need an `AtomicU64`, which is the lesson of 34.1 applied inside a concurrency-limiting pattern.

Variation. Replace the join-one-at-a-time structure with the MiniPool from 34.3: submit all the tasks, have each do `wait`, work, `post`, and use an `AtomicU64` for the completed count. It combines three of this chapter's patterns — a pool, a semaphore, an atomic — into the shape of a real rate-limited service, and watching them fit together is the point of the whole chapter.

34.7 Exercises

1. Comprehension. Explain why `count += 1` in two threads can lose an increment, and why `fetchAdd` cannot. Then explain why the rule is "atomic for one cell, mutex for a region," and give an example that tempts you to break it.

2. Producer–consumer. Change the `Queue` in 34.2 to hold pointers (`rawptr`) instead of `u64`s, and use it to pass two different kinds of job to a worker that switches on a small tag. Why must the tag travel with the pointer?

3. Thread pool. Add a `drain()` to the `MiniPool` that blocks until every submitted task has run, and use it to write a program that submits a thousand increment tasks and prints the final atomic count. Which of the two synchronisation tools (the queue lock, the atomic) protects which piece of state?

4. Parallel map. Time the parallel map against a plain loop for a vector of ten, ten thousand, and ten million elements, with two and eight workers. At what size does parallelism start to win, and what does that tell you about the overhead per task?

5. Async. Rewrite the pipeline in 34.5 with three stages connected by two channels, so that a middle stage reads from one and writes to the next. Where does the middle stage await, and why can it not do its work between two awaits without a task switch?

6. Semaphore. Implement a `tryAcquire` helper around `tryWait` that runs a task without blocking if a permit is free and reports failure if not. Describe a situation where trying and failing is better than waiting.

7. Correctness audit. Take the producer–consumer code and find every line that touches `items`, `count`, `head`, or `closed`. For each, name the lock that must be held and confirm from the code that it is. Then deliberately move one access outside the lock and explain what can now go wrong.

8. Design. You are building a web server with a fixed number of worker threads and a bounded request queue. Using this chapter's structures, describe the whole design — the queue, the pool, the bound — and say what happens to a request that arrives when the queue is full. Which is the right response, blocking or rejecting, and why?
