Chapter 28

Live Examples: Sorting, Searching, and Complexity

How Do You Measure a Program?

Suppose you write two programs that sort a list. Both produce the right answer. Which one is better? The obvious answer is "the faster one," so you time them. But timing is a measurement of everything at once: your processor, your compiler's optimisation level, whether the machine was busy, how many other programs were running, what the input happened to be. Run the experiment twice and you get two different answers. Run it on a friend's laptop and you get a third. The measurement moves whenever any of a hundred variables move, and none of those variables is the thing you actually want to know.

So computer science does not measure seconds. It measures work as a function of the size of the input. It asks: if you hand this program a list of a thousand items, how many basic steps does it take? Now hand it a list of two thousand. Did the number of steps double, or quadruple, or barely change? That relationship — steps as a function of n — is what we call the time complexity of the algorithm, and it is a property of the algorithm's shape, not of your particular machine. An O(n) algorithm doubles its work when you double the input; an O(n^2) algorithm quadruples it. That fact will still be true on a phone in twenty years.

This chapter is unusual in the "Live Examples" part of this book, because a third of it is theory. That is deliberate. You cannot work sorting and searching problems competently without a working understanding of growth rates, best and worst cases, and amortised cost; they are the vocabulary in which every solution in the rest of this part is described. So we spend the first several sections building the theory properly, with no code at all, and then we implement, in Coral, the canonical searching and sorting algorithms and analyse each one honestly.

If any of this feels abstract at first, hold on — let me put it plainly. Complexity is just a disciplined way of saying "what happens to the work when the input gets big?" A linear scan of a phone book gets slower in proportion to the number of names. Looking a name up by opening to the middle and halving your way in barely gets slower at all. That difference, formalised, is the entire subject.

A note on the imports these examples use. Everything here operates on the growable list, `import(lib) std::vec { Vec };`, and the variations that sort use `sortI32` from `import(lib) std::collections::sort { sortI32 };`. The integer and boolean types are built in. Each code block assumes those imports are present and is otherwise complete.

28.1 Counting Steps: The Naive Idea, and Why It Nearly Works

The first honest thing to do is to try to count operations. Take the simplest algorithm in the book, summing the elements of a list:

    i64 sumAll(Vec<i32>* v) {
        i64 total = 0;
        for (usize i = 0; i < v->count(); i += 1) {
            total += (i64)v->at(i);
        }
        return total;
    }

How many "steps" does this take for a list of n numbers? Line by line: one step to set `total` to 0; for each element, one comparison `i < n`, one array read, one addition, one increment `i += 1`; then one final comparison that fails and one return. If we decide an outer-loop pass costs 4 steps and the setup costs 2, the total is 4n + 2. That is a genuine, exact count of a particular definition of "step."

The problem is that "a particular definition of step" is doing a lot of work in that sentence. Did we count the array read as one step or as a step plus an address calculation? Does the compiler unroll the loop? Is the addition on a 64-bit register the same cost as on a memory location? If we answer differently, we get a different formula — 4n + 2, or 3n + 5, or 4.5n + 1 — and all of them are "correct" under some accounting. The exact constants are not stable facts about the algorithm; they are accidents of how we chose to count. What is stable, and what survives every re-counting, is the shape: the work grows in proportion to n. Twice the input, twice the work.

That observation is the seed of the whole theory. We keep the shape and throw away the constants, because the constants are noise and the shape is signal.

28.2 Big-O, Big-Omega, and Big-Theta: Three Bounds

The notation everyone has heard of is big-O, often written O(...). Its everyday description is "an upper bound on the growth." Precisely: we say a function f(n) is O(g(n)) if, for all sufficiently large n, f(n) grows no faster than some constant multiple of g(n). In symbols, there exists a positive constant c and a threshold n₀ such that for every n ≥ n₀, f(n) ≤ c · g(n).

Read that slowly, because it says something weaker than people assume. To say 4n + 2 is O(n) is to say there is a multiple of n that eventually stays on top of 4n + 2 — and there is: pick c = 5, and 5n ≥ 4n + 2 for all n ≥ 2. Big-O never claims the constant is tight, and it never claims g is the best possible bound. It says only "g is at least this big, eventually, up to a constant." That is why 4n + 2 is also O(n^2) and O(n^3) and O(2^n); every one of those is a valid upper bound, just a loose one. When a programmer says "this is O(n)," they usually mean the tightest simple upper bound they know, but the definition itself is loose.

The matching upper bound is big-Omega, Ω(...), which means "a lower bound on the growth." We say f(n) is Ω(g(n)) if, for all sufficiently large n, f(n) grows at least as fast as some constant multiple of g(n): there are c > 0 and n₀ with f(n) ≥ c · g(n) for all n ≥ n₀. If big-O is the ceiling, big-Omega is the floor. "Any comparison sort needs at least n log n comparisons in the worst case" is the statement that its worst-case cost is Ω(n log n).

When the ceiling and the floor are the same curve, we get big-Theta, Θ(...), the tight bound. We say f(n) is Θ(g(n)) if f is both O(g) and Ω(g): there are constants c₁, c₂ > 0 and a threshold n₀ such that c₁ · g(n) ≤ f(n) ≤ c₂ · g(n) for all n ≥ n₀. In words: f and g grow at the same rate, sandwiching each other between two constant multiples. The honest description of our sum function is "Θ(n)" — not merely "at most n-ish," but "exactly n-ish, up to constants."

There is a small discipline here that pays off when you read other people's analysis. If you know only an upper bound, say O. If you know only a lower bound, say Ω. Say Θ only when you have both and they match. A great many careless sentences say O when they mean Θ, and the looseness hides real information: "binary search is O(n)" is technically true (n is an upper bound on log n) and completely useless, because the whole point of binary search is that it is Θ(log n). Being precise about which bound you mean is not pedantry; it is the difference between an analysis and a shrug.

28.3 Growth Rates: The Table You Should Memorise

The functions that actually appear in algorithms are few, and their relative growth is the single most useful table in this subject. Columns are increasing n; rows are the common complexity classes. Read the last column to feel the difference.

    n          log2 n   n        n log2 n    n^2         2^n
    --------------------------------------------------------------
    10         3.3      10       33          100         1,024
    100        6.6      100      664         10,000      1.27 × 10^30
    1,000      10       1,000    9,966       1,000,000   ~10^301
    10,000     13.3     10,000   132,877     100,000,000 unthinkable
    1,000,000  19.9     10^6     19,931,569  10^12       no

A gentler way to read it: imagine a machine doing a billion operations per second, and an input of a million items. How long does each class take?

    Complexity      steps for n = 10^6   time at 10^9 steps/sec
    -----------------------------------------------------------
    O(log n)        ~20                   instant
    O(n)            10^6                  ~1 millisecond
    O(n log n)      ~2 × 10^7             ~20 milliseconds
    O(n^2)          10^12                 ~17 minutes
    O(2^n)          astronomically large  longer than the universe

Two lessons fall out of these tables. The first is that the ordering matters more than the constants. An O(n log n) sort with a clumsy inner loop beats an O(n^2) sort with a beautifully tight inner loop for every large input, because eventually the shape wins and no constant can rescue the worse shape. The second is that the cheap classes are almost free and the expensive ones are hopeless, with very little grace in between. The jump from n log n to n^2 is the difference between a coffee break and a coffee break that outlives you.

The classes in order of growth, smallest first, are: O(1) constant, O(log n) logarithmic, O(n) linear, O(n log n) "linearithmic," O(n^2) quadratic, O(n^3) cubic, O(2^n) exponential, O(n!) factorial. Constant means the work does not depend on n at all. Logarithmic means the work barely moves — halving a million-item problem takes only twenty halvings. Exponential means the work explodes with every added item, and that is why brute force over all subsets or all permutations ends at a very small n.

28.4 Best, Worst, and Average Case

An algorithm's cost usually depends on more than the size of the input; it depends on the input's contents. The same sorting routine takes different amounts of work on an already-sorted list and on a shuffled one. So we do not speak of one complexity; we speak of three.

The worst case is the most work the algorithm does over all inputs of size n. It is the number everyone quotes first, because it is a promise you can rely on: no matter what arrives, you will wait at most this long. The best case is the least work, and it is usually a curiosity — it describes an input so convenient that it rarely occurs. The average case is the expected work over some distribution of inputs, and it is the most honest for real use, but only if you know the distribution, which often you do not.

Quicksort makes all three concrete, and we will see it in 28.8. Its best and average case are Θ(n log n): the partition keeps splitting the input into roughly equal halves. Its worst case is Θ(n^2), and it is triggered by the one input a naive implementation is most likely to meet in the wild: a list that is already sorted. That is why the standard library's `partitionI32`, which we quoted back in Chapter 16, chooses the pivot by looking at the first, middle, and last elements rather than grabbing the last one — a small change that makes the sorted-input worst case far less likely.

The phrase "amortised" is sometimes confused with "average," and they are not the same, which brings us to the next section.

28.5 Amortised Analysis: Why Vec::push Is O(1)

Here is a puzzle. Look at `Vec<T>::push` from the standard library (Chapter 16 quotes the whole struct; the hinge is these lines):

    void push(T val) {
        if (self.len >= self.cap) {
            usize newCap = self.cap > 0 ? self.cap * 2 : 4;
            self.reserve(newCap);
        }
        self.data[self.len] = val;
        self.len++;
    }

Most of the time `push` does a constant amount of work: write one element, bump the length. But every so often — when the vector is full — it reallocates the backing array to twice the size and copies every existing element into the new one. That copy is O(n). So is `push` O(1) or O(n)? It is sometimes each.

The answer is that it is O(1) amortised, and amortised is a precise term, not a vague one. Amortised cost is the average cost per operation when you spread the total cost of a worst-case sequence of operations over that sequence. It is not "average case" (which would be over random inputs) and it is not "usually O(1)" (which would be hand-waving). It is a theorem about every sequence: no matter how an adversary orders the operations, a sequence of n pushes costs O(n) total, so the cost per push is O(1) on average over the sequence.

The proof is the doubling argument, and it is short enough to hold in your head. Suppose the capacity starts at 1 and doubles. Growing at sizes 1, 2, 4, 8, 16, ... costs copies of 1, 2, 4, 8, 16, ... elements. The total number of elements copied across all the growth steps up to a final size n is

    1 + 2 + 4 + ... + n/2 < n.

That is a geometric series, and its sum is less than twice the last term, so the whole history of copying is bounded by about n element-moves, not by n^2. Now count the n pushes themselves: n writes. So n pushes do at most n writes plus fewer than n copied moves, which is fewer than 2n operations total. Spread over n pushes, that is fewer than 2 operations each — a constant. Therefore each `push`, averaged over any long enough sequence, costs O(1), even though individual pushes occasionally cost O(n). The expensive pushes are rare precisely because the array doubled, and they are paid for by all the cheap ones before them.

This is the reason a dynamic array is the right default container despite the occasional big copy, and it is why the standard library doubles capacity rather than adding a fixed amount. If `push` grew by one each time instead, every push would copy the whole array and the amortised cost would be O(n) — the table of 28.3's quadratic row, imposed on the most basic operation. Doubling is the trick that turns "occasionally catastrophic" into "constant on average," and it is one of the small, deep pieces of engineering that you get for free by using the standard Vec.

28.6 Linear Search: The Baseline

The problem. Given a list of numbers and a target, find the index of the target, or report that it is not present.

Picture this. You have a stack of forms and you are looking for the one with a particular name. You pick up the first, read it, no; the second, no; and so on until you find it or run out. There is no cleverness available, because the forms are in no particular order — the one you want could be anywhere.

Brute force, then better. Linear search is itself the brute force. There is no better general method on an unsorted list, and that is a fact worth internalising: the "better approach" here is to sort the list first (if you will search it many times) and then use binary search. For a single lookup, the scan is optimal.

    i64 linearSearch(Vec<i32>* v, i32 key) {
        for (usize i = 0; i < v->count(); i += 1) {
            if (v->at(i) == key) return (i64)i;
        }
        return -1;
    }

The return type is i64, not usize, because we need a value to mean "not found" and every usize is a legal index. A signed type has room for −1, which is not a valid index, so it can carry the absent answer without stealing a real one. (The fully honest alternative, if you have read Chapter 15, is `Option<usize>`, which says "an index, or nothing" in the type and cannot be mistaken.)

Time and space. The loop runs at most n times, once per element, so it is Θ(n) time in the worst and average case and O(1) in the best case (the target is the first element). It uses O(1) extra space — just the counter. There is no way to beat Θ(n) on an unsorted list, and the argument is simple: if you have not looked at some element, that element could be the target, so any correct algorithm must, in the worst case, look at all of them.

Edge cases. An empty list returns −1 without the loop running; `v->count()` is 0 and the condition fails at once. Duplicates are fine, but note that the function returns the first match; if you need the last, scan backwards. The target being absent costs the full n steps, which is exactly the worst case, not an anomaly.

A variation. If the same list will be searched many times, sort it once with the `sortI32` from `std::collections::sort` and then use binary search for every query. The one-time cost is Θ(n log n) and every subsequent search is Θ(log n) instead of Θ(n). After roughly log n queries the sort has paid for itself, and after that it is pure profit. This trade — pay once, save many times — recurs constantly in algorithm design.

28.7 Binary Search: Halving the Problem

The problem. Given a list that is already sorted in ascending order, find the index of a target value, or report that it is absent — and do it without touching every element.

Picture this. You are looking up a word in a dictionary. Nobody starts at page one. You open to the middle, look at a word, and instantly learn which half the target is in: if the word you see comes before your target alphabetically, the target is in the right half; if after, the left. You throw away the wrong half entirely, open the middle of what remains, and repeat. Each step halves the pages you still have to consider. A thousand-page dictionary takes about ten steps, because 2^10 is about a thousand.

Brute force, then better. The brute force is 28.6's linear scan, Θ(n). Binary search exploits the ordering to be dramatically better: on each comparison it discards half the remaining elements, so the number of comparisons is the number of times you can halve n before reaching one, which is log₂ n.

    i64 binarySearch(Vec<i32>* v, i32 key) {
        i64 lo = 0;
        i64 hi = (i64)v->count() - 1;
        while (lo <= hi) {
            i64 mid = lo + (hi - lo) / 2;
            i32 val = v->at((usize)mid);
            if (val == key) return mid;
            if (val < key) lo = mid + 1;
            else hi = mid - 1;
        }
        return -1;
    }

The bounds are inclusive: `lo` and `hi` are both positions that might still hold the target, and the loop runs while the window is non-empty (`lo <= hi`). The midpoint is computed as `lo + (hi - lo) / 2` rather than the equivalent-looking `(lo + hi) / 2`. The two are mathematically the same, but the second can overflow when lo and hi are both large — their sum exceeds the range even though the average fits — and that overflow is a famous, decades-old bug in binary search implementations from C's standard library onward. Writing the subtraction first keeps every intermediate value inside the range. When the target is smaller, we move `hi` below `mid`; larger, `lo` above it. When they cross, the window is empty and the target is absent.

Time and space. Each iteration halves the window, so the number of iterations is Θ(log n): about 20 for a million elements, about 30 for a billion. The space is O(1) — three integers and a few locals — because the version above iterates rather than recurses. (A recursive binary search is equally Θ(log n) time but pays Θ(log n) stack, a needless cost.) The speeding-up is the whole point: where linear search needed a million steps, binary search needs twenty.

Edge cases. The list must be sorted; if it is not, binary search returns nonsense without any error, which is its great danger. An empty list gives `hi = -1`, so `lo <= hi` is `0 <= -1`, false, and it returns −1 correctly. A one-element list checks that element. Duplicates: this version returns some matching index, not necessarily the first or last; if you need the first occurrence, keep searching left after a hit instead of returning immediately. The signed indices again matter — `(i64)v->count() - 1` for an empty vector is −1, not a wrapped-around giant.

A variation. "Binary search on the answer" is a powerful pattern that does not look like searching a list. When a problem asks for the smallest value that satisfies a monotone condition — the smallest capacity that lets a ship deliver all packages in D days, say — you binary-search the range of candidate answers, testing each candidate with a linear scan. The candidate space is a virtual sorted list, and the halving works exactly the same. Sorting and searching are not just things you do to arrays; they are ways of thinking about any space with an order.

28.8 Quicksort

The problem. Sort a list of numbers in place, in ascending order, as fast as possible on typical inputs and without allocating a second array.

Picture this. You pick one item from the pile — the pivot — and you sort the rest into two sub-piles: smaller than the pivot, and larger. You set the pivot down between them; it is now in its final place. Then you turn to each sub-pile and do the same thing, recursively, until the sub-piles are too small to bother with. Notice that you never compare items from different sub-piles, and you never move the pivot again.

Brute force, then better. The brute force is repeated selection: find the minimum, move it to the front, find the next minimum, and so on — Θ(n^2). Quicksort's insight is that a single partition around a pivot places one element permanently and divides the work, so the two halves can be sorted independently. In the good case each partition splits the list roughly in half, and the recursion depth is log n with n work per level, giving Θ(n log n).

    i64 partition(Vec<i32>* v, i64 lo, i64 hi) {
        i32 pivot = v->at((usize)hi);
        i64 i = lo - 1;
        for (i64 j = lo; j < hi; j += 1) {
            if (v->at((usize)j) <= pivot) {
                i += 1;
                swapAt(v, i, j);
            }
        }
        swapAt(v, i + 1, hi);
        return i + 1;
    }

    void quickSortRange(Vec<i32>* v, i64 lo, i64 hi) {
        if (lo >= hi) return;
        i64 p = partition(v, lo, hi);
        quickSortRange(v, lo, p - 1);
        quickSortRange(v, p + 1, hi);
    }

    void quickSort(Vec<i32>* v) {
        quickSortRange(v, 0, (i64)v->count() - 1);
    }

    void swapAt(Vec<i32>* v, i64 a, i64 b) {
        i32 tmp = v->at((usize)a);
        v->set((usize)a, v->at((usize)b));
        v->set((usize)b, tmp);
    }

`partition` is the engine. It takes the last element as the pivot and walks `j` across the range, keeping everything at or below index `i` smaller than the pivot. Whenever it finds a small element it advances `i` and swaps that element into the small region. At the end, `i + 1` is the correct home for the pivot, so it swaps the pivot there and returns its index. `quickSortRange` then recurses on the two sides of that index, which are now independent: nothing in the left half will ever compare to anything in the right half.

Time and space. The average and best cases are Θ(n log n): if each partition splits the range roughly evenly, there are log n levels of recursion and each level does O(n) partition work. The worst case is Θ(n^2), and it happens when the pivot is always the smallest or largest remaining element, splitting off one element at a time — which is exactly what a naive last-element pivot does to an already-sorted or reverse-sorted list. Space is O(log n) on average for the recursion, and O(n) in the worst case. The standard library's `partitionI32` chooses the pivot by looking at the first, middle, and last elements and taking the median — the "median of three" trick — which makes the sorted-input worst case all but disappear at trivial extra cost.

Edge cases. An empty or single-element list is handled by `lo >= hi` returning immediately. A list of all-equal elements: with `<=` in the comparison, every element joins the small region, so the pivot lands at the far right and the split is lopsided — the classic worst case hiding in plain sight. Randomising the pivot, or using median-of-three, cures it. Quicksort is not stable: equal elements can end up in a different relative order than they started. That only matters when you sort records by a key and expect ties to keep their input order, and it is the main reason merge sort (28.9) is preferred for such cases.

A variation. For small ranges, quicksort's recursion overhead dominates. A common optimisation is to switch to insertion sort when the range has fewer than, say, 16 elements, then stop the recursion entirely; the array becomes "almost sorted" and one final insertion-sort pass finishes it in linear time. Real library sorts do exactly this, and it is why the theoretical O(n log n) and the measured time are closer than the rough analysis alone would suggest.

28.9 Mergesort

The problem. Sort a list of numbers in ascending order, in guaranteed Θ(n log n) time in every case, stably (equal elements keep their relative order).

Picture this. You have two piles of cards, each already sorted. To merge them into one sorted pile you look at the top card of each and take the smaller, over and over. That is the whole merge step, and it is linear. Now to sort an unsorted pile, you split it in half, sort each half (by the same method), and merge the two sorted halves. Each split halves the problem, and each level of splitting does a linear pass of merging, giving log n levels times n work per level.

Brute force, then better. The brute force is the same selection sort as before, Θ(n^2). Mergesort beats it in the worst case as well as the average, because it does not depend on a lucky pivot: the split is always in the middle by construction. The price is the second array used for merging, which quicksort avoids.

    void merge(Vec<i32>* v, Vec<i32>* scratch, i64 lo, i64 mid, i64 hi) {
        i64 i = lo;
        i64 j = mid + 1;
        i64 k = lo;
        while (i <= mid && j <= hi) {
            if (v->at((usize)i) <= v->at((usize)j)) {
                scratch->set((usize)k, v->at((usize)i));
                i += 1;
            } else {
                scratch->set((usize)k, v->at((usize)j));
                j += 1;
            }
            k += 1;
        }
        while (i <= mid) { scratch->set((usize)k, v->at((usize)i)); i += 1; k += 1; }
        while (j <= hi)  { scratch->set((usize)k, v->at((usize)j)); j += 1; k += 1; }
        for (i64 t = lo; t <= hi; t += 1) {
            v->set((usize)t, scratch->at((usize)t));
        }
    }

    void mergeSortRange(Vec<i32>* v, Vec<i32>* scratch, i64 lo, i64 hi) {
        if (hi - lo <= 0) return;
        i64 mid = lo + (hi - lo) / 2;
        mergeSortRange(v, scratch, lo, mid);
        mergeSortRange(v, scratch, mid + 1, hi);
        merge(v, scratch, lo, mid, hi);
    }

    void mergeSort(Vec<i32>* v) {
        usize n = v->count();
        Vec<i32> scratch = Vec<i32>::withCap(n);
        for (usize t = 0; t < n; t += 1) {
            scratch.push(0);
        }
        mergeSortRange(v, &scratch, 0, (i64)n - 1);
    }

`mergeSortRange` splits the range at the midpoint, sorts each half, and merges. `merge` is the two-cards-at-a-time walk: while both runs still have elements, take the smaller front; then copy whatever remains of whichever run is left. The `scratch` vector is allocated once and reused by every merge, which is what keeps the auxiliary cost at O(n) instead of the O(n log n) you would pay by allocating inside each call. The comparison uses `<=`, which is what makes mergesort stable: when the two fronts are equal, the one from the left run (which came first in the original input) is taken first.

Time and space. The recursion splits into two halves at every level, and there are log n levels; each level's total merging work is linear because every element is copied once per level. So the time is Θ(n log n) in the best, average, and worst cases — there is no pathological input. The space is the auxiliary `scratch` array, O(n), plus O(log n) for the recursion. Mergesort is the "safe" sort: slightly slower than quicksort on typical in-memory data due to the copying, but with no bad cases and with stability guaranteed.

Edge cases. An empty list allocates a zero-length scratch and returns. A single element does nothing. Stability is the property to remember: if you sort a list of (name, score) pairs by score, equal scores will stay in their original name order, which quicksort does not promise. That makes mergesort the right choice for sorting by one key while preserving another, and it is why several standard libraries use a mergesort variant for their general sort.

A variation. Mergesort is the canonical "external sort," the sort used when the data does not fit in memory. You sort chunks that do fit, write each sorted chunk to disk, then repeatedly merge the sorted chunks. The merge step is streaming and needs only a few elements of each run in memory at once, so the same algorithm scales from a thousand items to a hundred billion.

28.10 Heapsort

The problem. Sort a list in place in guaranteed Θ(n log n) time, using no auxiliary array.

Picture this. Line the numbers up in the shape of a heap — a triangle where every parent is larger than its children. The largest element is then sitting at the very top, and you know where it is without searching. You swap it to the end of the array (its final place), shrink the heap by one, and restore the heap property around the new top. Repeat. Each pass removes the maximum and re-heaps in logarithmic time.

Brute force, then better. The brute force is to repeatedly scan the remaining elements for the maximum and move it to the end, which is Θ(n^2). Heapsort keeps the maximum readily available by maintaining the heap, so instead of a linear scan you do a logarithmic sift-down. The clever part is that the heap is stored directly in the array you are sorting — no separate tree, no extra memory.

    void siftDown(Vec<i32>* v, i64 n, i64 i) {
        while (true) {
            i64 largest = i;
            i64 l = 2 * i + 1;
            i64 r = 2 * i + 2;
            if (l < n && v->at((usize)l) > v->at((usize)largest)) largest = l;
            if (r < n && v->at((usize)r) > v->at((usize)largest)) largest = r;
            if (largest == i) break;
            swapAt(v, i, largest);
            i = largest;
        }
    }

    void heapSort(Vec<i32>* v) {
        i64 n = (i64)v->count();
        for (i64 i = n / 2 - 1; i >= 0; i -= 1) {
            siftDown(v, n, i);
        }
        for (i64 end = n - 1; end > 0; end -= 1) {
            swapAt(v, 0, end);
            siftDown(v, end, 0);
        }
    }

A heap in an array uses no pointers: the children of the element at index i are at 2i+1 and 2i+2, and its parent is at (i−1)/2. `siftDown` restores the heap property at one position by repeatedly swapping with the larger child until the element is bigger than both, or reaches the bottom. The first loop builds a max-heap from the unsorted array by sifting down every internal node from the last up; the second loop repeatedly swaps the top (the current maximum) into the last position and sifts the new top down over the shrinking heap. After the second loop's k-th step, the largest k elements sit in their final positions at the end of the array.

Time and space. Building the heap is O(n) (a classic result: most nodes are near the bottom and sift only a little). Each of the n removals sifts down O(log n), for Θ(n log n) total, in the best, average, and worst cases. The space is O(1) — it sorts in place, using only indices — which is the property that distinguishes it from mergesort. In practice heapsort is usually a little slower than a well-tuned quicksort because its accesses jump around the array and stress the cache, but its worst case is the good case, so it is a common fallback when quicksort's recursion gets too deep.

Edge cases. An empty list: `n / 2 - 1` is `-1`, the build loop does not run, and the removal loop does not run. A single element is likewise untouched. Heapsort is not stable, like quicksort. The `l < n` and `r < n` bounds checks are essential: near the bottom of the heap, the child index can be past the end of the array, and reading it would be out of bounds.

A variation. The same `siftDown` machinery, with the comparison reversed, gives a min-heap, which is exactly how `PriorityQueue` in `std::collections` is built (Chapter 16 walked through its `_siftUp` and `_siftDown`). A priority queue is a heap whose only operations are push and pop-the-minimum; heapsort is what you get if you push everything and then pop everything. Learning one teaches the other.

28.11 Counting Sort: When You Can Beat n log n

The problem. Sort a list of integers, where every value is known to be between 0 and some maximum k that is not much larger than the number of elements n.

Picture this. You have a pile of survey responses, each an answer from 1 to 5, and you want them in order. You do not compare answers. You just make five labelled boxes and drop each response into its box; then you read the boxes out in order. The work is one drop per response — linear — plus the reading of the boxes, which is proportional to the number of boxes. No comparisons are made at all.

Brute force, then better. Every sort so far compares pairs of elements, and there is a theorem that any comparison sort needs Ω(n log n) comparisons in the worst case. Counting sort sidesteps the theorem entirely by not comparing: it counts how many of each value there are, then writes the values out in order. When the range of values k is close to n, this is faster than any comparison sort.

    void countingSort(Vec<i32>* v, i32 maxValue) {
        usize k = (usize)maxValue + 1;
        Vec<i32> count = Vec<i32>::withCap(k);
        for (usize i = 0; i < k; i += 1) {
            count.push(0);
        }
        for (usize i = 0; i < v->count(); i += 1) {
            i32 value = v->at(i);
            count.set((usize)value, count.at((usize)value) + 1);
        }
        usize out = 0;
        for (usize value = 0; value < k; value += 1) {
            i32 howMany = count.at(value);
            for (i32 r = 0; r < howMany; r += 1) {
                v->set(out, (i32)value);
                out += 1;
            }
        }
    }

The `count` vector has one slot per possible value, and the first loop tallies how often each value appears: `count[value]` ends up holding the number of copies of `value`. The second loop walks the values in increasing order and writes each one out as many times as it was counted. There is no comparison anywhere; the ordering comes from the loop's direction, not from judging pairs.

Time and space. If n is the number of elements and k is the range of values, the time is Θ(n + k): one pass to count, one pass over the value range to emit. When k is O(n) — say all values fit in a small band — this is Θ(n), strictly better than the Θ(n log n) comparison lower bound. The space is Θ(k) for the count array. That is the trade the algorithm makes: it spends memory proportional to the range of values to buy linear time, and it is therefore a poor choice when k is huge (sorting a million numbers that range up to a billion would need a billion-slot count array), and a poor choice when the values are not integers at all.

Edge cases. Negative values are not handled; the usual fix is to find the minimum first and offset every value by it, so the range starts at zero. The declared `maxValue` must actually be the maximum in the list, or elements above it index past the end of `count` — an out-of-bounds write waiting to happen, which is why signatures often compute the range rather than trust a caller. An empty list does nothing. When k is much larger than n, this algorithm is slower and greedier than a comparison sort, and that is the case to avoid it in.

A variation. Radix sort generalises counting sort to large integer ranges by sorting one digit at a time, using a stable counting sort on each digit from least significant to most. It runs in Θ(d · (n + b)) for d digits in base b, which for fixed-width integers is effectively linear, and it is how large libraries sort fixed-size keys. It also illustrates why stability matters: each digit pass must preserve the order established by the previous pass, and only a stable sort does that.

28.12 Choosing a Sort

The table of the five sorts, side by side, is the summary of this chapter:

    algorithm      best        average      worst        space     stable
    ----------------------------------------------------------------------
    quicksort      n log n     n log n      n^2          log n     no
    mergesort      n log n     n log n      n log n      n         yes
    heapsort       n log n     n log n      n log n      1         no
    counting sort  n + k       n + k        n + k        k         yes
    insertion      n           n^2          n^2          1         yes

The choices are not academic. If you need a guaranteed worst case and stability, choose mergesort. If you need in-place sorting with a good average case and can tolerate a bad worst case, choose quicksort — and defend against the bad case with a randomised or median-of-three pivot. If you need a guaranteed worst case and minimal memory, choose heapsort. If your keys are small integers, choose counting sort and laugh at the comparison sorts. If your list is tiny (under a dozen or so elements), insertion sort is faster than all of them, which is why production sorts switch to it for small ranges.

Two general lessons close the theory. First, the comparison lower bound of Ω(n log n) is not a limitation of any one sort; it is a limitation of the entire strategy of comparing elements. The only way past it is to stop comparing, as counting sort does, which requires the extra structure of a small key range. Second, the right question is never "which sort is fastest" in the abstract. It is "what do I know about my data?" — its size, its key range, whether ties matter, whether it fits in memory — and the answer to that question picks the sort.
