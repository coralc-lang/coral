Chapter 26

Live Examples: Stacks, Queues, and Linked Lists

The Shapes of Ordered Access

The last two chapters stored things and looked them up. This chapter is about the *order* in which you get them back, and about a way of storing things that is not an array at all. Three structures carry the whole chapter, and each is best introduced by a homely rule.

A stack is a pile of plates. You put a plate on top and you take a plate off the top; the last plate you put down is the first one you pick up. Last in, first out. The rule sounds trivial, and yet it is the engine behind undo, behind matching brackets, behind the call stack that runs every recursive function you have ever written.

A queue is a checkout line. You join at the back and you are served at the front; the first person in is the first person through. First in, first out. The rule behind task scheduling, breadth-first search, and any problem where things must be handled in the order they arrive.

A linked list is a treasure hunt. Each clue does not tell you where the treasure is — it tells you where the next clue is. There is no "clue number 5"; you reach the fifth clue by following four arrows. That is both its power (you can insert a clue between two others by rewriting one arrow) and its weakness (to reach a clue you must walk there, and walking means jumping around memory instead of sliding along a contiguous array, which the processor's cache does not like). Chapter 16 introduced the standard library's `LinkedList<T>`; here we mostly build our own nodes, because the point is to manipulate the arrows directly, which is exactly what the classic list problems ask you to do.

One note before the code. Coral has no separate `Stack` type, and that is not an omission. A stack is a `Vec` used with two operations, `push` and `pop`, and naming that usage is a comment, not a type. A queue is a `Deque` used at one end, or the library's thin `Queue` wrapper; the underlying ring buffer lives in `std::collections.deque` and `ringbuf` (Chapter 16, 16.6). When a problem says "use a stack," reach for a `Vec`; when it says "use a queue," reach for a `Queue` or a `Deque`. The data structure in the algorithm is a pattern of access, and Coral's containers are the storage that supports the pattern.

26.1 Valid Parentheses

The problem

Given a string of the characters `()[]{}`, decide whether the brackets are balanced: every opener is closed by the matching kind, in the right order.

Picture this

A stack of open brackets. When you see an opener, you put it on the pile. When you see a closer, you take the top opener off the pile and check that it is the matching kind. If the pile is empty when a closer arrives, the closer has nothing to close. If, at the end, the pile is not empty, some opener was never closed. Both of those are failures, and the order is checked automatically because the *nearest* unmatched opener is always the one on top.

Brute force

Repeatedly scan the string and delete adjacent matching pairs until no pair is left; if the string is empty, it balanced. Each scan is linear and you might need many scans, so it is quadratic. It is also awkward to implement because deletion in the middle shifts everything.

The better approach

One pass and a stack. Opener, push. Closer, pop and verify. At the end, the stack must be empty. The stack enforces the "most recent unmatched opener closes first" rule for free, which is the nesting rule.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    bool isValid(str s) {
        Vec<u8> stack = Vec<u8>::new();
        for (usize i = 0; i < s.len; i++) {
            u8 c = s.at(i);
            if (c == '(' || c == '[' || c == '{') {
                stack.push(c);
            } else {
                if (stack.isEmpty()) {
                    return false;
                }
                u8 open = stack.pop();
                if (c == ')' && open != '(') return false;
                if (c == ']' && open != '[') return false;
                if (c == '}' && open != '{') return false;
            }
        }
        return stack.isEmpty();
    }

Two lines do most of the work. The `stack.isEmpty()` check at the top of the closing branch catches a closer with nothing to match — the input `")"` fails there. And the final `return stack.isEmpty()` catches the opposite failure, an unmatched opener, as in `"("`. A naive version that forgot the final check would accept `"("` and every broken string that begins with an extra opener.

The cost

Time is linear: each character is pushed at most once and popped at most once, so the stack work is bounded by the length. Space is linear in the worst case — a string of all openers — because the stack holds every unmatched opener. This is a case where the extra memory is genuinely proportional to the input, and that is unavoidable: the answer depends on how deep the nesting goes, and the depth is exactly what the stack measures.

Edge cases and a variation

An empty string is valid, and the loop returns true from the final check. A string with an odd length can never be valid; you could add `if (s.len % 2 == 1) return false;` as a cheap early exit. The variation: allow the wildcard `*` to stand for an opener, a closer, or nothing at all, which turns a one-pass check into a small dynamic-programming or greedy-with-stack problem. A second variation, very common in real code, is to report *where* the first mismatch is rather than just a yes or no, by pushing the *index* of each opener instead of the character; the extra information costs nothing and turns the function into a diagnostic.

26.2 Min Stack

The problem

Design a stack that, in addition to push and pop, can return its minimum element, all in constant time.

Picture this

A stack of boxes where each box, alongside its content, also carries a note saying "the smallest item at or below me." The note is cheap to maintain: when a new box goes on, its note is the smaller of its own content and the note on the box beneath it. Then the smallest item in the whole stack is simply the note on the top box, read in one glance.

Brute force

Keep the stack, and when asked for the minimum, scan all the elements. That is linear per query, which fails the constant-time requirement.

The better approach

Two stacks, or one stack of paired values. The first stack holds the data. The second stack, the "minimum stack," holds at each level the minimum of everything from the bottom up to that level. Pushing a value pushes `min(value, currentMin)` onto the minimum stack; popping the data stack pops the minimum stack in lockstep. The top of the minimum stack is always the answer. This is the note-on-every-box idea made explicit.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    struct MinStack {
        Vec<i32> data;
        Vec<i32> mins;

        static MinStack new() {
            return MinStack {
                .data = Vec<i32>::new(),
                .mins = Vec<i32>::new()
            };
        }

        void push(i32 v) {
            self.data.push(v);
            if (self.mins.isEmpty() || v <= self.mins.back()) {
                self.mins.push(v);
            } else {
                self.mins.push(self.mins.back());
            }
        }

        void pop() {
            self.data.pop();
            self.mins.pop();
        }

        i32 top() {
            return self.data.back();
        }

        i32 getMin() {
            return self.mins.back();
        }

        bool isEmpty() {
            return self.data.isEmpty();
        }
    }

The `v <= self.mins.back()` comparison is deliberately non-strict. If a new value equals the current minimum, both copies must go on the minimum stack, because both will need to come off as the data stack pops past them. Using a strict `<` would drop one of the equal minima and the minimum stack would underflow its meaning when the first of the two popped away. This is the same "equal values are not duplicates to be merged" subtlety as the second-largest problem in Chapter 23.

The cost

Every operation is constant time. The data stack's cost is the same as any Vec stack — constant amortized. The minimum stack adds one more push and pop per operation, also constant, so the query is constant as required. Space is linear, but it is twice the space of a plain stack; that doubling is the price of the constant-time minimum, and it is worth asking whether your problem needs the query often enough to pay it. This is the constant-time trade: precompute a little with every write so every read is free.

Edge cases and a variation

Pushing onto an empty stack makes the value the minimum, handled by the `mins.isEmpty()` branch. Calling `getMin` on an empty stack is a misuse; the underlying `back` asserts, which is the correct loud failure from Chapter 15. The variation with a much smaller memory footprint: instead of storing the minimum at every level, store only the *changes* to the minimum. Keep a single minimum and a stack of the old minima pushed only when a new smaller value arrives, popping when the current minimum is the value being removed. That is constant time and, on inputs that rarely decrease, far less memory.

26.3 Evaluate Reverse Polish Notation

The problem

Evaluate an arithmetic expression in reverse Polish (postfix) notation, where operators come after their operands: `["2", "1", "+", "3", "*"]` means `(2 + 1) * 3 = 9`.

Picture this

Reading postfix is like assembling a value from the bottom up. Each number is a completed piece; each operator takes the two most recently completed pieces, combines them, and leaves the single result as the new most recent piece. The "most recently completed" rule is exactly a stack: numbers go on, and an operator pops two and pushes one.

Brute force

There is no meaningful slower approach — postfix evaluation is naturally linear — but the naive implementation keeps a list and, at each operator, searches backward for the two operands and splices them out. That search makes it quadratic and obscures the elegance. The stack makes the "two most recent" idea literal.

The better approach

One pass. On a number, push it. On an operator, pop the right operand, pop the left operand (note the order), apply, and push the result. At the end, exactly one value remains on the stack, and it is the answer.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { parseI64, println };

    bool isOperator(str t) {
        if (t.len != 1) return false;
        u8 c = t.at(0);
        return c == '+' || c == '-' || c == '*' || c == '/';
    }

    i32 applyOp(u8 op, i32 a, i32 b) {
        if (op == '+') return a + b;
        if (op == '-') return a - b;
        if (op == '*') return a * b;
        return a / b;
    }

    i32 evalRPN(const Vec<str>* tokens) {
        Vec<i32> stack = Vec<i32>::new();
        for (usize i = 0; i < tokens->count(); i++) {
            str t = tokens->at(i);
            if (isOperator(t)) {
                i32 b = stack.pop();
                i32 a = stack.pop();
                stack.push(applyOp(t.at(0), a, b));
            } else {
                bool ok = false;
                i64 n = parseI64(t, &ok);
                stack.push((i32)n);
            }
        }
        return stack.pop();
    }

The single most important line is which operand is popped first. `b` is popped before `a`, and then `applyOp` is called as `applyOp(op, a, b)`, so for subtraction and division the order is right: `b` was the top of the stack and therefore the *right* operand. Reversing these two pops is the classic bug in every RPN evaluator, and it produces programs that are correct for addition and multiplication and wrong only for subtraction and division — the worst kind of bug, because half your test cases pass.

The cost

Time is linear: one pass, constant work per token (a push, or two pops and a push). Space is linear in the worst case, when the input is a long run of numbers before any operator, because the stack must hold them all.

Edge cases and a variation

A well-formed expression leaves exactly one value; an expression that is malformed would underflow the stack, and the `pop` assertion catches it loudly. Integer division truncates toward zero in Coral, matching the usual problem statement. Overflow of intermediate results is the real risk; promote the stack to `i64` if the inputs are large. The variation: build the expression tree instead of evaluating it, by pushing node pointers rather than numbers and, on an operator, popping two subtrees and pushing a new operator node. That produces an abstract syntax tree — the `Expr` variant of Chapter 13 — which you can then evaluate, pretty-print, or compile, and it shows that a stack is a tool for building trees from postfix order, not just for arithmetic.

26.4 Daily Temperatures

The problem

Given a list of daily temperatures, for each day return how many days you must wait until a warmer day. If no warmer day comes, the answer for that day is 0.

Picture this

A line of days, each waiting to be told when it will be beaten by a warmer day. The trick is the monotonic stack. We keep a stack of days that are still *waiting*, and we keep them in decreasing order of temperature from bottom to top. When a new, warmer day arrives, it resolves every waiting day on the stack that it beats, so those days are popped and their answers recorded. The stack never holds a day after the day that beats it arrives, and the days are resolved in the order they are beaten.

Brute force

For each day, look forward until you find a warmer day. That is quadratic in the worst case — a strictly decreasing temperature list makes every search scan to the end.

The better approach

One pass with a stack of *indices* whose temperatures are waiting. For each new day i, while the stack is non-empty and today's temperature is greater than the temperature at the top index, pop that index j and record `i - j` as its answer. Then push i as a new waiting day. Days left on the stack at the end never got a warmer day, so their answers stay at the initialized zero.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    Vec<i32> dailyTemperatures(const Vec<i32>* t) {
        Vec<i32> out = Vec<i32>::new();
        for (usize i = 0; i < t->count(); i++) {
            out.push(0);
        }

        Vec<usize> stack = Vec<usize>::new();
        for (usize i = 0; i < t->count(); i++) {
            while (!stack.isEmpty() && t->at(i) > t->at(stack.back())) {
                usize j = stack.pop();
                out.set(j, (i32)(i - j));
            }
            stack.push(i);
        }
        return out;
    }

The stack stores indices rather than temperatures, and that is not an accident: it lets a later day compute the wait `i - j` for the day it beats. Storing only the temperature would resolve the comparison but lose the position, and the answer is a distance. The comparison is strict `>` so that equal temperatures do not resolve each other — a day is only ended by a *warmer* one, not an equally warm one.

The cost

Time is linear, and again the nested `while` is deceptive. Each index is pushed exactly once and popped at most once, so across the entire run the inner loop performs at most n pops. Space is linear in the worst case — a strictly decreasing list keeps every index on the stack — but that is the input that needs it.

Edge cases and a variation

An empty or single-element list answers with all zeroes; the loop handles both. Equal temperatures keep both days waiting, so the earlier day is not resolved by its equal twin, which is correct. The variation: instead of waiting for a warmer day, compute the next *greater* element to the right for each position — the same monotonic decreasing stack, and the same idea. Change "warmer" to "colder" and you use a monotonic increasing stack instead. The monotonic stack is a general tool: whenever a problem asks "for each element, find the next element that beats it," the answer is usually a monotonic stack, and the only design choice is which order the stack maintains.

26.5 Implement a Queue Using Two Stacks

The problem

Implement a first-in-first-out queue using only two stacks, and support enqueue and dequeue.

Picture this

You have two piles of plates and must serve the oldest first. You enqueue onto one pile, the "in" pile. To dequeue, you move plates one at a time from the in pile to the out pile, which reverses their order, and then take from the top of the out pile. Because the reversal happens only when the out pile is empty, each plate is moved at most once, and the service order is exactly the arrival order. The two piles together have the memory of a line.

Brute force

With a single stack you cannot do it: a stack serves the newest first, which is the opposite of a queue. One could copy the whole stack into a temporary on every dequeue, but that is O(n) per dequeue and gives nothing over the two-stack design.

The better approach

Two stacks, `inStack` and `outStack`. Enqueue pushes onto `inStack`. Dequeue, when `outStack` is empty, pours every element of `inStack` into `outStack` — the reverses — then pops from `outStack`. The amortized cost per operation is constant, even though a single dequeue can cost O(n) when it triggers a pour. The key is that each element is poured at most once per arrival, so the total work across all operations is linear.

The implementation

    import(lib) std::vec { Vec };
    import(lib) std::io::ios { println };

    struct StackQueue {
        Vec<i32> inStack;
        Vec<i32> outStack;

        static StackQueue new() {
            return StackQueue {
                .inStack = Vec<i32>::new(),
                .outStack = Vec<i32>::new()
            };
        }

        void enqueue(i32 v) {
            self.inStack.push(v);
        }

        i32 dequeue() {
            if (self.outStack.isEmpty()) {
                while (!self.inStack.isEmpty()) {
                    self.outStack.push(self.inStack.pop());
                }
            }
            return self.outStack.pop();
        }

        bool isEmpty() {
            return self.inStack.isEmpty() && self.outStack.isEmpty();
        }

        usize count() {
            return self.inStack.count() + self.outStack.count();
        }
    }

The lazy pour is the heart of it. If we poured on every enqueue instead, each element could be moved many times; by pouring only on a dequeue that finds the out stack empty, and pouring everything at once, each element moves exactly twice in its lifetime — once into the in stack, once into the out stack. That is what makes the amortized cost constant.

The cost

A single enqueue is constant. A single dequeue is O(n) in the worst case, when it triggers a pour of n elements, but the *amortized* cost — the total work divided by the number of operations — is constant, because each element is poured once. This is the first genuine amortized analysis in these chapters, and it is the same reasoning that makes a growing `Vec`'s pushes constant on average (Chapter 16): an occasional expensive operation paid for by many cheap ones. Space is linear.

Edge cases and a variation

Dequeuing from an empty queue asserts, which is the correct loud failure. An enqueue followed by a dequeue works on the first pour. The variation with a practical note: the standard library already ships a queue, `std::collections::queue { Queue }`, whose `enqueue`, `dequeue`, and `peek` are constant time every call because it is a ring buffer, not two stacks (Chapter 16, 16.6). The two-stack queue is a *classic interview problem* — it exists to test whether you understand amortized analysis and the relationship between the two orderings — not a thing you should ship when the library has the real one. Knowing when a clever construction is a teaching exercise and when it is production code is part of the skill.

26.6 Reverse a Linked List

The problem

Given the head of a singly linked list, reverse it and return the new head.

Picture this

Reversing a chain of arrows is a matter of walking the chain and turning each arrow around as you pass. You need three fingers: one on the node *before* the current one, one on the current node, and one on the node after, because you are about to overwrite the current node's arrow and would otherwise lose your place. That third finger — the "next" saved before the rewrite — is the detail everyone forgets the first time.

Brute force

Copy the values into an array, then rebuild the list in reverse. That is linear time and linear extra space, and it treats the list as if it were an array, which misses the point of the exercise: the whole difficulty is manipulating the links in place.

The better approach

Iterate with three pointers. Save `next`, point the current node's `next` backward at `prev`, then advance all three. When the current node falls off the end, `prev` is standing on the new head. Each node's arrow is flipped exactly once.

The implementation

    import(lib) std::mman { alloc, dealloc };
    import(lib) std::io::ios { println };

    struct Node {
        i32 value;
        Node* next;
    }

    Node* newNode(i32 v) {
        Node* n = alloc<Node>(1);
        n->value = v;
        n->next = null;
        return n;
    }

    Node* reverseList(Node* head) {
        Node* prev = null;
        Node* cur = head;
        while (cur != null) {
            Node* next = cur->next;
            cur->next = prev;
            prev = cur;
            cur = next;
        }
        return prev;
    }

The recursion version is a nice mirror of the same idea and worth seeing, because it shows what the explicit "next" finger is doing:

    Node* reverseRec(Node* head) {
        if (head == null || head->next == null) {
            return head;
        }
        Node* newHead = reverseRec(head->next);
        head->next->next = head;
        head->next = null;
        return newHead;
    }

The recursive version reverses the tail first and then stitches the current node onto the end of the reversed tail. It is shorter and it is worse: it uses stack space proportional to the list length, so a list of a hundred thousand nodes can overflow the call stack, while the iterative version uses constant space. This is the rare case where the prettier code is the wrong code, and it is the reason the iterative version is the one to remember.

The cost

Iterative: linear time, one pass, constant space for the three pointers. Recursive: linear time but linear space for the call stack. The asymptotic time is the same; the space is the difference, and for lists it is often the difference between working and crashing. Freeing the nodes is a separate concern from reversing them — see the exercises — and this is the boundary between an algorithm and the ownership discipline of Chapter 11: the algorithm rearranges pointers, but it does not decide who owns the memory.

Edge cases and a variation

An empty list returns null; a single-node list returns that node unchanged, and both fall out of the loops. The variation: reverse only the sub-list between positions `m` and `n`, leaving the rest attached. It uses the same three-pointer walk, with a saved node before the start of the interval and one extra stitch at the end, and it is a good exercise in keeping the outside connections straight while flipping the inside ones.

26.7 Merge Two Sorted Linked Lists

The problem

Given the heads of two sorted linked lists, merge them into one sorted list and return its head, reusing the existing nodes.

Picture this

Two sorted queues of cards. You repeatedly compare the two front cards, take the smaller, and append it to the output. Because both inputs are sorted, the smallest remaining card is always at one of the two fronts, so the greedy choice is the correct one. A placeholder node, called a dummy, sits at the front of the output so you do not have to special-case the very first card; you keep a finger on the last output node and extend from it.

Brute force

Collect both lists into arrays, concatenate, sort, and rebuild. That throws away the sortedness both inputs already have, costs O((m+n) log(m+n)) instead of O(m+n), and allocates.

The better approach

Merge in place with a dummy head and a tail pointer. While both lists have a node, append the smaller one and advance that list. When one list runs out, append the entire remainder of the other — it is already sorted and already linked, so it is a single pointer assignment, not a loop. Finally, free the dummy and return its next.

The implementation

    import(lib) std::mman { alloc, dealloc };
    import(lib) std::io::ios { println };

    struct Node {
        i32 value;
        Node* next;
    }

    Node* newNode(i32 v) {
        Node* n = alloc<Node>(1);
        n->value = v;
        n->next = null;
        return n;
    }

    Node* mergeTwoLists(Node* a, Node* b) {
        Node* dummy = newNode(0);
        Node* tail = dummy;
        while (a != null && b != null) {
            if (a->value <= b->value) {
                tail->next = a;
                a = a->next;
            } else {
                tail->next = b;
                b = b->next;
            }
            tail = tail->next;
        }
        tail->next = (a != null) ? a : b;
        Node* result = dummy->next;
        dealloc<Node>(dummy);
        return result;
    }

The `<={` comparison is what makes the merge stable: when the two fronts are equal, the node from `a` comes first, preserving the original relative order of equal elements. Change it to `<` and equal elements from `b` jump ahead of their equals from `a`, which is a legitimate merge but a different one. The dummy node is the other trick worth naming: without it, the first output node would need its own branch to be installed as the head, and every other iteration would need a different path. The dummy turns "first" into "just another" and removes the special case.

The cost

Time is linear in the combined length: each iteration consumes one node, and the trailing append of the remainder is constant. Space is constant — a handful of pointers and one temporary dummy node that is freed before returning. The nodes themselves are reused, not copied, so no allocation happens inside the loop at all.

Edge cases and a variation

If either input is empty, the loop does not run and the entire other list is appended, which is correct. If both are empty, the result is null. The variation: merge k sorted lists. Better than merging them two at a time, whose cost is O(N log k) where N is the total length and one full list is rescanned at each level of the pairwise reduction, you keep a min-heap of the k current fronts and repeatedly pop the smallest — O(N log k) with no rescans — which is exactly Chapter 16's `PriorityQueue`. The same greedy choice, generalized with the right data structure.

26.8 Linked List Cycle

The problem

Decide whether a linked list contains a cycle — a node whose `next` eventually leads back to a node already in the list.

Picture this

Two runners on the same track. One runs at one step per tick, the other at two. If the track is a straight line, the fast runner pulls away and eventually reaches the end. If the track loops, the fast runner enters the loop first, and then, sooner or later, laps the slow runner from behind. The moment they stand on the same spot, you know there is a loop. This is Floyd's tortoise-and-hare, and it needs no extra memory at all.

Brute force

Walk the list and record every visited node in a set. If you ever arrive at a node already in the set, there is a cycle. That is linear time but linear extra space — and if the nodes had no comparable identity, you would be storing pointers, which is fine but wasteful for a question this simple.

The better approach

Two pointers, slow and fast. Advance slow by one and fast by two each iteration. If fast ever falls off the end, there is no cycle. If slow and fast ever point at the same node, there is a cycle. Constant space, and the running time is linear because the fast pointer closes the gap by one node each tick once both are inside the loop.

The implementation

    import(lib) std::mman { alloc, dealloc };
    import(lib) std::io::ios { println };

    struct Node {
        i32 value;
        Node* next;
    }

    Node* newNode(i32 v) {
        Node* n = alloc<Node>(1);
        n->value = v;
        n->next = null;
        return n;
    }

    bool hasCycle(Node* head) {
        Node* slow = head;
        Node* fast = head;
        while (fast != null && fast->next != null) {
            slow = slow->next;
            fast = fast->next->next;
            if (slow == fast) {
                return true;
            }
        }
        return false;
    }

The loop condition must check both `fast != null` and `fast->next != null` before the body dereferences `fast->next->next`. Checking only `fast` would be enough for the first of the two hops but not the second, and the missing guard is a null dereference waiting for any list of even length. This is the same discipline as the two-pointer loops in Chapter 24: whenever a pointer takes two steps, both steps must be guarded.

The cost

Time is linear. In the acyclic case the fast pointer reaches the end after about n/2 ticks. In the cyclic case, once both pointers are in the loop the distance between them shrinks by one each tick, so they meet within one loop length. Space is constant — two pointers and nothing else, which is the point of using Floyd's algorithm over the set-marking version.

Edge cases and a variation

An empty list and a single node with no self-loop both return false. A node that points to itself forms a cycle of length one, and the loop detects it on the first iteration because `slow` and `fast` both land on it. The variation, and a lovely one: not only *whether* there is a cycle but *where* it begins. Once the two pointers meet, move one pointer back to the head and advance both one step at a time; they meet again exactly at the entry node of the cycle. The proof is a short piece of arithmetic on the distances traveled, and implementing it is the standard follow-up. The same tortoise-and-hare idea also solves Chapter 25's Happy Number in constant space, which is a nice sign that you have understood the pattern rather than memorized it for lists.
