Chapter 30

Live Examples: Graphs

The Shape Behind Half of Computer Science

A graph is the simplest interesting thing after a list: a set of points and a set of connections between them. The points are called vertices, the connections are called edges, and the moment you have both you have a model for an astonishing range of problems. Roads between cities, friendships between people, links between web pages, dependencies between build tasks, wires between chips, moves in a game, reactions in a cell. Every one of those is vertices and edges, and every one of them has been attacked with the same handful of algorithms, which is why learning those algorithms once pays off in every domain you will ever touch.

Two kinds of graph, and the distinction matters from the very first line of code. In an undirected graph, an edge goes both ways: a road from A to B is also a road from B to A, so a friendship is mutual. In a directed graph, an edge has a direction: a dependency means "task A must finish before task B starts," and it does not mean the reverse. Many algorithms work on both with a one-line change; others care deeply which kind they are given, and knowing which is your job.

There is also the question of how to store a graph, and the answer is a trade worth stating plainly. An adjacency list is one list per vertex, holding that vertex's neighbours. It uses memory proportional to the number of edges, and it makes "who are my neighbours" fast, which is what almost every traversal asks. An adjacency matrix is a grid of booleans (or weights), with entry (u, v) saying whether u and v are connected; it makes "are these two connected" a single lookup, and it uses memory proportional to the square of the number of vertices. For sparse graphs — few edges relative to vertices, which the real world usually produces — the adjacency list wins by a mile. Unless a problem specifically needs constant-time edge queries, reach for the list. This chapter uses `Vec<Vec<...>>`: an outer vector indexed by vertex, each entry an inner vector of neighbours. It is the adjacency list, expressed with the containers of Chapter 16.

A word on the size of these algorithms, so the rest of the chapter reads easily. Almost every traversal here is O(V + E) — the cost of looking at every vertex and every edge once. Dijkstra adds a heap and becomes O((V + E) log V). Kruskal adds a sort and a union-find and becomes O(E log E). That small vocabulary of costs describes nearly everything in this chapter, and by now, after Chapter 28, you can read every one of them as "what happens when the input grows."

A note on the imports these examples use. The graph is built from `import(lib) std::vec { Vec };`, BFS and Kahn's algorithm use `import(lib) std::collections::queue { Queue };`, the heaps in Dijkstra and Prim use `import(lib) std::collections::priorityqueue { PriorityQueue };`, and sorting edges by weight uses the `sortBy` method on `Vec`. Each relevant code block repeats the import it needs so it can be read on its own.

30.1 Representing a Graph

The problem. Build a graph type in Coral that can hold an undirected or directed graph with integer-named vertices, supports adding edges, and exposes each vertex's neighbours efficiently.

Picture this. A graph is a city map. Each intersection has a signpost listing the streets that leave it. The adjacency list is a filing cabinet with one drawer per intersection; the drawer holds exactly the streets from that intersection. To find where you can go next, you open one drawer, not the whole cabinet.

Brute force, then better. The naive representation is an adjacency matrix: an n×n grid of booleans, where `matrix[u][v]` is true if u and v are connected. It is simple and gives O(1) edge queries, but it stores n^2 entries whether or not there are that many edges, which for a million-vertex, few-edge graph is a trillion booleans — absurd. The adjacency list stores only the edges that exist, and every traversal in this chapter walks neighbours, so the list is both smaller and better shaped for the work.

    import(lib) std::vec { Vec };

    struct Graph {
        usize n;
        Vec<Vec<i32>> adj;

        static Graph new(usize n) {
            Graph g = Graph {
                .n = n,
                .adj = Vec<Vec<i32>>::new()
            };
            for (usize i = 0; i < n; i += 1) {
                g.adj.push(Vec<i32>::new());
            }
            return g;
        }

        void addUndirectedEdge(i32 u, i32 v) {
            self.adj.atPtr((usize)u)->push(v);
            self.adj.atPtr((usize)v)->push(u);
        }

        void addDirectedEdge(i32 u, i32 v) {
            self.adj.atPtr((usize)u)->push(v);
        }
    }

The struct holds the vertex count and a `Vec<Vec<i32>>`: an outer vector with one slot per vertex, each slot itself a vector of neighbour indices. `new` allocates n empty inner vectors so that `adj[u]` is always a valid drawer, even for an isolated vertex. `addUndirectedEdge` pushes each endpoint into the other's list, which is what makes the edge mutual; `addDirectedEdge` pushes only from u to v, which is what makes it one-way. The `atPtr` in both methods is deliberate: it returns a pointer to the inner vector without copying it, and pushing through that pointer is safe. Writing `self.adj.at(u)->push(v)` would copy the inner `Vec`, note that `Vec` owns heap memory, and risk the copy and the original both being freed — the classic double-free footgun when a container of owning containers is accessed by value.

Time and space. Building a graph with V vertices costs O(V) to create the drawers, and each `addEdge` is O(1). The storage is O(V + E), where E is the number of edges, because the outer vector holds V drawers and the inner vectors together hold 2E entries for an undirected graph. Contrast the matrix, which would be O(V^2) storage. For any graph that is not nearly complete, the list is the better representation.

Edge cases. A graph with zero vertices is legal and empty; loops over its vertices simply do not run. An undirected self-loop (u, u) is handled correctly by the code, though whether it is meaningful depends on the problem. Duplicate edges are not deduplicated; if a problem can supply them, either deduplicate at insert time or write the traversal to tolerate revisiting, which most do anyway.

A variation. For weighted graphs, store a struct per edge instead of a bare int:

    struct Edge {
        i32 to;
        i32 weight;
    }

Then the adjacency list becomes `Vec<Vec<Edge>>`, and each neighbour carries its edge weight. Dijkstra (30.5) and Prim (30.8) use exactly this. The alternative — a Map from a pair to a weight — is far clumsier for the traversal-at-neighbours work these algorithms do, which is why weighted edges are usually stored alongside the neighbour, not separately.

30.2 BFS: Shortest Paths in an Unweighted Graph

The problem. Given an unweighted graph and a source vertex, find the number of edges on the shortest path from the source to every other vertex. This is the "fewest hops" distance, and it is the foundation of an enormous number of graph problems.

Picture this. You are in a strange city, and you want the fewest street-crossings to reach each corner. You start at your corner and mark it "zero." Then you visit every corner one step away and mark them "one." Then every unvisited corner two steps away, and mark them "two," and so on. You never revisit a corner, because the first time you reach it is necessarily by the shortest route — if there were a shorter route you would have found it in an earlier ring. That expanding-ring process is breadth-first search.

Brute force, then better. The brute force for shortest paths is to explore every possible walk, which is exponential because walks can loop forever. BFS is smarter because it visits vertices in order of distance and stops as soon as a vertex is first reached; the first visit is the shortest visit, and no edge ever needs to be examined again for that vertex. The tool that makes this happen is a queue: first-in, first-out, so the vertices at distance d are all dequeued before any at distance d+1.

    import(lib) std::collections::queue { Queue };

    void bfs(Graph* g, i32 source, Vec<i32>* dist) {
        for (usize i = 0; i < g->n; i += 1) {
            dist->push(-1);                       // -1 means "not reached yet"
        }
        dist->set((usize)source, 0);
        Queue<i32> q = Queue<i32>::new();
        q.enqueue(source);
        while (!q.isEmpty()) {
            i32 u = q.dequeue();
            Vec<i32>* neighbors = g->adj.atPtr((usize)u);
            for (usize i = 0; i < neighbors->count(); i += 1) {
                i32 v = neighbors->at(i);
                if (dist->at((usize)v) == -1) {
                    dist->set((usize)v, dist->at((usize)u) + 1);
                    q.enqueue(v);
                }
            }
        }
    }

The `dist` vector doubles as the visited marker: −1 means "never seen" and any non-negative number means "seen, at this distance." The source starts at distance 0 and goes into the queue. The loop pulls a vertex, walks its neighbours, and whenever it finds an unvisited one, records its distance as one more than the current vertex's and enqueues it. Because the queue is FIFO, a vertex is discovered by the closest possible predecessor, and its recorded distance is therefore the true shortest.

Time and space. Every vertex is enqueued at most once, and every edge is examined once from each endpoint (twice total for an undirected graph), so the time is O(V + E). The distance vector is O(V), and the queue holds at most O(V) vertices. BFS is linear in the size of the graph, which is the best any traversal can do, since it must at least look at every vertex and edge.

Edge cases. The source is distance 0 from itself. Vertices in other connected components stay at −1, which is the correct report: they are unreachable. A graph with no edges gives every non-source vertex −1. Negative distances never arise, so a signed type for `dist` is natural; the −1 sentinel is safe because real distances are non-negative. If the graph is weighted, BFS's distances are wrong — it counts edges, not weights — and you want Dijkstra instead.

A variation. To reconstruct the actual shortest path, not just its length, keep a `parent` vector alongside `dist` and record `parent[v] = u` when you discover v. Then walk backward from any target to the source. This "parent pointer" trick is how route-finding programs produce not just "how far" but "which way," and it adds only O(V) memory.

30.3 DFS: Connected Components and Cycle Detection

The problem. Two tasks that share one algorithm. First, count the connected components of an undirected graph (the groups of mutually reachable vertices). Second, detect whether a directed graph contains a cycle.

Picture this. Connected components are groups of islands joined by bridges. Standing on one island, you can walk to some set of other islands and no further; that set is its component. To count them, you visit every island you can from a starting point, then look for the next one you have not visited and start again. Depth-first search is one way to do the walking: you go as deep as you can along one path before backing up, like exploring a maze by always taking the first unexplored corridor.

Brute force, then better. There is no better-than-linear way to visit every vertex, so DFS is the algorithm. Its shape is a recursion that marks the current vertex and then recurses into every unvisited neighbour. The recursion stack plays the role the queue played in BFS; the only difference is the order of exploration.

    void dfsFrom(Graph* g, i32 u, Vec<bool>* visited) {
        visited->set((usize)u, true);
        Vec<i32>* neighbors = g->adj.atPtr((usize)u);
        for (usize i = 0; i < neighbors->count(); i += 1) {
            i32 v = neighbors->at(i);
            if (!visited->at((usize)v)) {
                dfsFrom(g, v, visited);
            }
        }
    }

    i32 countComponents(Graph* g) {
        Vec<bool> visited = Vec<bool>::new();
        for (usize i = 0; i < g->n; i += 1) {
            visited.push(false);
        }
        i32 count = 0;
        for (usize u = 0; u < g->n; u += 1) {
            if (!visited.at(u)) {
                count += 1;
                dfsFrom(g, (i32)u, &visited);
            }
        }
        return count;
    }

`dfsFrom` visits one vertex and floods outward through every unvisited neighbour, marking as it goes. `countComponents` restarts that flood from every vertex not yet reached, and each restart is a new component. The `&visited` at each call is essential: the visited set must be the same set across the entire flood, not a fresh copy per call, or the algorithm would revisit vertices forever.

For cycle detection in a directed graph, DFS needs to know more than "visited." A vertex is white (untouched), gray (on the current recursion path), or black (finished). A cycle exists exactly when an edge leads to a gray vertex — a back edge into the path we are still walking. An edge to a black vertex is harmless: that vertex is done and cannot close a loop back to us. Three states with names, and never a fourth, is exactly what an enum is for (Chapter 13):

    enum Color {
        White,
        Gray,
        Black,
    }

    bool dfsCycle(Graph* g, i32 u, Vec<Color>* state) {
        state->set((usize)u, Color::Gray);        // on the current path
        Vec<i32>* neighbors = g->adj.atPtr((usize)u);
        for (usize i = 0; i < neighbors->count(); i += 1) {
            i32 v = neighbors->at(i);
            Color c = state->at((usize)v);
            if (c == Color::Gray) return true;    // back edge: a cycle
            if (c == Color::White && dfsCycle(g, v, state)) return true;
        }
        state->set((usize)u, Color::Black);       // finished
        return false;
    }

    bool hasCycle(Graph* g) {
        Vec<Color> state = Vec<Color>::new();
        for (usize i = 0; i < g->n; i += 1) {
            state.push(Color::White);
        }
        for (usize u = 0; u < g->n; u += 1) {
            if (state.at(u) == Color::White && dfsCycle(g, (i32)u, &state)) return true;
        }
        return false;
    }

The three-colour scheme is the whole idea, and it is worth stating plainly: white means "not yet explored," gray means "currently on the path from the start," black means "explored completely." An edge into gray closes a loop; an edge into black does not. Using an `enum` rather than bare integers means the comparison reads as the concept — `c == Color::Gray` — and a mistyped `2 == 3` can never masquerade as a colour test.

Time and space. Both algorithms visit every vertex once and every edge once, so both are O(V + E) time. The recursion stack is O(V) deep in the worst case (a long chain of vertices), and the visited or state array is O(V). The stack depth is why DFS on a very large graph may need an explicit stack instead of recursion, exactly as Chapter 27 warned for deep trees.

Edge cases. An empty graph has zero components and no cycle. A graph of isolated vertices has one component per vertex and no cycle. For undirected cycle detection, the three-colour scheme is not right — the edge back to your own parent looks like a cycle — and the usual fix is to ignore the parent when recursing. The directed version is what this code implements. A self-loop is a cycle of length one and is detected because the vertex is gray while examining its own edge.

A variation. DFS also produces a topological order of a directed acyclic graph: push each vertex onto a list after all its neighbours are finished (a postorder), then reverse it. That is the DFS cousin of the queue-based topological sort in 30.4, and both are worth knowing because interviewers and libraries use both.

30.4 Topological Sort: An Order That Respects Dependencies

The problem. Given a directed acyclic graph, produce a linear ordering of the vertices such that every edge points from earlier to later. If the graph has a cycle, no such ordering exists, and the algorithm should say so. The motivating example is a build system: "compile A before B" is an edge A→B, and the topological order is a legal build order.

Picture this. You are getting dressed, and some garments depend on others: socks before shoes, shirt before jacket. You want a list of all garments in an order with no contradictions. A workable rule: repeatedly take any garment that has nothing left depending on it before you put it on — that is, any garment with no unfinished prerequisites — and remove it from the pile, which may free up others. If at some point nothing is free and items remain, those items depend on each other in a cycle and no order exists.

Brute force, then better. The brute force tries to build an order by trial and error, exponential. Kahn's algorithm is the elegant linear method: count each vertex's incoming edges (its "indegree"), repeatedly output a vertex with indegree zero, and decrement its neighbours' indegrees as if removing it. A vertex becomes available exactly when its last prerequisite has been removed.

    bool topologicalSort(Graph* g, Vec<i32>* order) {
        Vec<i32> indegree = Vec<i32>::new();
        for (usize i = 0; i < g->n; i += 1) {
            indegree.push(0);
        }
        for (usize u = 0; u < g->n; u += 1) {
            Vec<i32>* neighbors = g->adj.atPtr(u);
            for (usize i = 0; i < neighbors->count(); i += 1) {
                i32 v = neighbors->at(i);
                indegree.set((usize)v, indegree.at((usize)v) + 1);
            }
        }
        Queue<i32> q = Queue<i32>::new();
        for (usize u = 0; u < g->n; u += 1) {
            if (indegree.at(u) == 0) q.enqueue((i32)u);
        }
        while (!q.isEmpty()) {
            i32 u = q.dequeue();
            order->push(u);
            Vec<i32>* neighbors = g->adj.atPtr((usize)u);
            for (usize i = 0; i < neighbors->count(); i += 1) {
                i32 v = neighbors->at(i);
                indegree.set((usize)v, indegree.at((usize)v) - 1);
                if (indegree.at((usize)v) == 0) {
                    q.enqueue(v);
                }
            }
        }
        return order->count() == g->n;
    }

The first pass computes every vertex's indegree by walking all edges. The queue is seeded with the zero-indegree vertices — the ones with no prerequisites, which may be one or many. The main loop removes a vertex, appends it to the order, and "deletes" its outgoing edges by decrementing each neighbour's indegree; a neighbour whose count hits zero has had all its prerequisites satisfied and is enqueued. The final check is the clever part: if the order does not contain every vertex, some vertices never became free, which can only happen if they are locked in a cycle. So the same pass detects acyclicity, no separate cycle check needed.

Time and space. Computing indegrees is O(V + E), and the main loop processes each vertex and edge once, so the total is O(V + E). The indegree vector is O(V) and the queue is O(V). If the graph has several valid topological orders, the algorithm returns one of them; the tie is broken by the order vertices were enqueued, which is deterministic for a given input.

Edge cases. An empty graph produces an empty order and reports success. A graph with a cycle produces an order shorter than V and returns false, which is the correct "impossible" signal. Multiple valid orders are expected and not a bug; any of them is a correct answer. Self-loops are immediate cycles: a vertex with a self-edge has indegree at least one and can never be freed.

A variation. The DFS postorder version of topological sort (mentioned in 30.3) produces an ordering by pushing vertices after their descendants finish, then reversing. Its advantage is that it comes for free if you are already doing a DFS; its disadvantage is that detecting a cycle requires the three-colour machinery of 30.3, whereas Kahn's detects it from the output length alone. 30.9 shows the canonical application: deciding whether a set of courses can all be taken given prerequisites.

30.5 Dijkstra: Shortest Paths with Positive Weights

The problem. Given a weighted graph with non-negative edge weights and a source vertex, find the length of the shortest path from the source to every other vertex.

Picture this. You are driving between cities, and each road has a travel time. The shortest route to a city is the shortest route to one of its neighbours plus the road from that neighbour, minimised. That is optimal substructure again, and it suggests DP — but the graph has no natural order to fill a table, because a city can be reached through any of many predecessors. Dijkstra's insight is to always finalise the nearest unfinalised vertex next, which turns the unordered graph into an ordered process.

Brute force, then better. The brute-force way to find shortest paths is to consider all paths, which is exponential because of loops. A simpler correct method, Bellman–Ford, relaxes every edge V−1 times and handles even negative weights, at O(V × E). Dijkstra is faster — O((V + E) log V) — but only for non-negative weights. It uses a priority queue to always pull the vertex with the smallest tentative distance, which is the one whose distance can no longer improve.

    struct Edge {
        i32 to;
        i32 weight;
    }

    struct QNode {
        i64 dist;
        i32 node;
    }

    bool qNodeLess(QNode a, QNode b) {
        return a.dist < b.dist;
    }

    void dijkstra(Vec<Vec<Edge>>* adj, usize n, i32 source, Vec<i64>* dist) {
        i64 infinity = 1000000000000000000;      // a stand-in for "unreachable"
        for (usize i = 0; i < n; i += 1) {
            dist->push(infinity);
        }
        dist->set((usize)source, 0);
        PriorityQueue<QNode> pq = PriorityQueue<QNode>::new(qNodeLess);
        pq.push(QNode { .dist = 0, .node = source });
        while (!pq.isEmpty()) {
            QNode top = pq.pop();
            i32 u = top.node;
            if (top.dist > dist->at((usize)u)) continue;   // a stale, outdated entry
            Vec<Edge>* neighbors = adj->atPtr((usize)u);
            for (usize i = 0; i < neighbors->count(); i += 1) {
                Edge e = neighbors->at(i);
                i64 candidate = top.dist + (i64)e.weight;
                if (candidate < dist->at((usize)e.to)) {
                    dist->set((usize)e.to, candidate);
                    pq.push(QNode { .dist = candidate, .node = e.to });
                }
            }
        }
    }

The `dist` vector holds the best known distance to each vertex, starting at infinity for all but the source (distance 0). The priority queue, ordered so the smallest distance comes out first, holds pairs of (tentative distance, vertex). Pulling the smallest such pair finalises that vertex: because all weights are non-negative, no later path can ever be shorter, so its distance is settled. Then the algorithm "relaxes" each outgoing edge: if going through u gives a shorter route to a neighbour, record it and push the new pair. The `if (top.dist > dist->at(u)) continue;` line discards stale entries — pairs that were pushed before a better distance was found — which is the standard "lazy deletion" approach that avoids needing a decrease-key operation on the heap.

Time and space. Each edge causes at most one push, so there are O(E) heap operations, each O(log E); the total is O((V + E) log V). The distance array and heap are O(V) and O(E) respectively. The log factor is the price of always knowing the nearest unfinished vertex; without a heap, Dijkstra is O(V^2), which is fine for dense graphs and worse for sparse ones.

Edge cases. Unreachable vertices stay at infinity, which is the correct report. The non-negative-weight requirement is a hard precondition: with a negative edge, the "finalised" vertex might later be improved, and the algorithm silently returns wrong answers. If negative weights are possible, use Bellman–Ford. The use of i64 for distances even though weights are i32 prevents overflow when many edges are added and provides a safe infinity. A single vertex graph returns just the source at distance 0.

A variation. Dijkstra returns distance only; to return the path, add a `parent` array set when a vertex's distance improves, then walk backward from the target. This is the same parent-pointer trick as BFS. A* is Dijkstra plus a heuristic that estimates distance to the goal, which lets it explore toward the target instead of uniformly in all directions — the algorithm inside most game pathfinding, and a direct extension of this one.

30.6 Union-Find: Keeping Track of Groups

The problem. Maintain a collection of disjoint groups that changes over time. Support two operations: `find(x)`, which reports which group x is in, and `unite(a, b)`, which merges the groups containing a and b. A third operation, "are a and b in the same group," falls out of `find`.

Picture this. You are running a mixer and people keep forming into conversation circles. `find(person)` asks which circle someone is in; `unite(a, b)` merges two circles when their members start talking. To answer quickly, you do not reassign everyone's group label by hand. Instead, each circle has one designated leader, and every person remembers only who told them which circle they were in — a pointer toward the leader. To find someone's circle, follow the pointers to the leader. Merging two circles just points one leader at the other.

Brute force, then better. The naive method relabels every member when two groups merge, which is O(n) per merge and O(n^2) overall. Union-find keeps the labels indirect: each element points to a parent, and only the roots are meaningful group labels. Two refinements make it fast. Union by rank attaches the smaller tree under the larger, keeping trees shallow. Path compression, during `find`, points every element on the path directly at the root, flattening the tree for future lookups.

    struct DSU {
        Vec<i32> parent;
        Vec<i32> rank;

        static DSU new(usize n) {
            DSU d = DSU {
                .parent = Vec<i32>::new(),
                .rank = Vec<i32>::new()
            };
            for (usize i = 0; i < n; i += 1) {
                d.parent.push((i32)i);            // each element starts as its own root
                d.rank.push(0);
            }
            return d;
        }

        i32 find(i32 x) {
            i32 root = x;
            while (self.parent.at((usize)root) != root) {
                root = self.parent.at((usize)root);
            }
            i32 cur = x;
            while (self.parent.at((usize)cur) != root) {
                i32 next = self.parent.at((usize)cur);
                self.parent.set((usize)cur, root);   // compress: point straight at the root
                cur = next;
            }
            return root;
        }

        bool unite(i32 a, i32 b) {
            i32 ra = self.find(a);
            i32 rb = self.find(b);
            if (ra == rb) return false;              // already together
            i32 rankA = self.rank.at((usize)ra);
            i32 rankB = self.rank.at((usize)rb);
            if (rankA < rankB) {
                self.parent.set((usize)ra, rb);
            } else if (rankA > rankB) {
                self.parent.set((usize)rb, ra);
            } else {
                self.parent.set((usize)rb, ra);
                self.rank.set((usize)ra, rankA + 1);
            }
            return true;
        }
    }

Each element's `parent` points to another element; a root points to itself, which is how you recognise it. `find` walks up to the root (first loop), then walks the same path again and repoints every element directly at the root (second loop) — the compression that keeps future finds short. `unite` finds both roots and hangs the shallower tree under the deeper one, using `rank` as a proxy for depth; only when the ranks tie does the depth actually increase, and the rank is bumped. The `false` return when the roots already match is the signal that a and b were already connected, which is exactly what Kruskal's algorithm needs.

Time and space. With both union by rank and path compression, the amortised cost of each operation is O(α(n)), the inverse Ackermann function, which is smaller than 5 for every n that fits in the universe. For all practical purposes, that is O(1). The storage is O(n) for the two arrays. Union-find is one of the rare data structures whose analysis is a genuine theorem, and the surprising conclusion is that the operations are effectively free.

Edge cases. Every element starts in its own singleton group, which is why `new(n)` initialises n groups. `find` on an out-of-range index is a bug the code does not guard, so callers must respect the bounds. A `unite(a, a)` returns false because the roots already match. The rank array is only a heuristic; omitting path compression still gives O(log n) per operation, and omitting union by rank can make it O(n) in the worst case, so keep both.

A variation. Union-find answers "connected?" for a graph as edges are added, which is the online version of 30.3's connected components. If the graph only ever grows, union-find is faster and simpler than re-running DFS for each query. If edges can also be removed, neither union-find nor DFS handles it directly, and you need a more elaborate structure — a good reminder that every data structure has a direction it does not go.

30.7 Kruskal's Minimum Spanning Tree

The problem. Given a connected undirected weighted graph, find a subset of edges that connects all vertices with the minimum possible total weight. Such a subset is always a tree (it has exactly V−1 edges and no cycles) and is called a minimum spanning tree.

Picture this. You are wiring a new office: every desk must be reachable from the network, but cable is expensive and you never want to run more than you must. You would consider all possible cables in order of cost, cheapest first, and lay each one down if it connects two previously separate clusters. When a cable would just loop back into an already-connected cluster, skip it. The cheapest cables come first, and the "skip anything that closes a loop" rule guarantees you never pay for a redundant connection.

Brute force, then better. Trying every subset of V−1 edges is exponential. Kruskal's algorithm is greedy and correct: sort the edges by weight, then add each to the tree unless it would create a cycle. The "would it create a cycle" test is exactly union-find's `unite`-returns-false test, which is what makes Kruskal fast.

    struct WEdge {
        i32 u;
        i32 v;
        i32 weight;
    }

    bool wEdgeLess(WEdge a, WEdge b) {
        return a.weight < b.weight;
    }

    i64 kruskal(usize n, Vec<WEdge>* edges) {
        if (n == 0) return 0;
        edges->sortBy(wEdgeLess);
        DSU dsu = DSU::new(n);
        i64 total = 0;
        usize used = 0;
        for (usize i = 0; i < edges->count(); i += 1) {
            WEdge e = edges->at(i);
            if (dsu.unite(e.u, e.v)) {
                total += (i64)e.weight;
                used += 1;
                if (used == n - 1) break;         // a spanning tree has n-1 edges
            }
        }
        if (n > 0 && used != n - 1) return -1;    // the graph was not connected
        return total;
    }

The algorithm is almost entirely in its two lines of English. Sorting by weight puts the cheap edges first. The loop tries each edge; `unite` returns true only when the edge joins two different components, in which case it is added and the running total updated. The moment n−1 edges have been added, the tree is complete and the loop breaks early. If the loop finishes without reaching n−1, some vertices were never connectable, and −1 reports that.

Time and space. The sort is O(E log E), and the loop does at most E union-find operations, each effectively O(1), so the total is O(E log E). The space is O(V + E) for the graph and the DSU arrays. Kruskal is the sort-heavy MST algorithm, and it is the right choice when the edge list is what you have; when the adjacency structure is already in hand, Prim (30.8) may be a better fit.

Why greedy works here. The cut property: for any partition of the vertices into two non-empty sets, the cheapest edge crossing the cut belongs to some minimum spanning tree. Kruskal's "add the cheapest edge that connects two components" is always adding a cheapest crossing edge for the cut between those components, so it never makes an unsafe choice. As with interval scheduling, the correctness rests on a proof, and the proof is what separates a greedy algorithm from a greedy guess.

Edge cases. An empty or single-vertex graph has total 0 with no edges. A disconnected graph cannot have a spanning tree; the function returns −1. Negative weights are fine: Kruskal never relies on weights being positive, only on their order. Duplicate edges of equal weight are fine; whichever is tried first may be taken, and the total is the same. Self-loops are rejected automatically, because `unite(u, u)` returns false.

A variation. The maximum spanning tree is the same algorithm with the sort reversed — one character changes and the greedy proof flips with it. And if the graph is complete and you want the MST by edge count rather than weight, Kruskal still works but Prim with a heap is often the faster implementation in practice.

30.8 Prim's Minimum Spanning Tree

The problem. The same minimum spanning tree as 30.7, but grown differently: start from one vertex and repeatedly add the cheapest edge that reaches a vertex not yet in the tree.

Picture this. You are lighting a town street by street, and you can only build from where you already have power. You start at one house, and at each step you light the nearest dark house reachable by a single wire from the lit area. The lit region grows like a snowball, and the wire you add each time is the cheapest joining the lit to the dark. When every house is lit, the wires you laid are an MST.

Brute force, then better. The brute force for the next cheapest crossing edge is a linear scan of all edges, giving O(V^2) for the whole algorithm. A priority queue turns each step's scan into a heap extraction: push every edge from the newly lit house to a dark one, then pop the cheapest overall, skipping edges whose dark endpoint has since been lit. That gives O((V + E) log V).

    i64 prim(Vec<Vec<Edge>>* adj, usize n) {
        if (n == 0) return 0;
        Vec<bool> inTree = Vec<bool>::new();
        for (usize i = 0; i < n; i += 1) {
            inTree.push(false);
        }
        PriorityQueue<QNode> pq = PriorityQueue<QNode>::new(qNodeLess);
        pq.push(QNode { .dist = 0, .node = 0 });       // start anywhere; no edge is "free"
        i64 total = 0;
        i32 reached = 0;
        while (!pq.isEmpty() && reached < (i32)n) {
            QNode top = pq.pop();
            i32 u = top.node;
            if (inTree.at((usize)u)) continue;          // already connected; stale entry
            inTree.set((usize)u, true);
            total += top.dist;
            reached += 1;
            Vec<Edge>* neighbors = adj->atPtr((usize)u);
            for (usize i = 0; i < neighbors->count(); i += 1) {
                Edge e = neighbors->at(i);
                if (!inTree.at((usize)e.to)) {
                    pq.push(QNode { .dist = (i64)e.weight, .node = e.to });
                }
            }
        }
        if (reached != (i32)n) return -1;
        return total;
    }

The priority queue holds (cost of the edge that would reach this vertex, vertex). It starts with the source at cost 0 — an artificial "edge" so the source is added first. Each iteration pops the cheapest way to reach a new vertex; if that vertex is already in the tree, the entry is stale and discarded. Otherwise the vertex joins the tree, its incoming cost is added to the total, and all its edges to still-dark neighbours are pushed as candidate ways in. The `reached` counter double-checks that every vertex made it in; if not, the graph is disconnected and −1 is returned.

Time and space. Each edge is pushed at most once (from each endpoint, so up to twice), and each heap operation is O(log V), for O((V + E) log V). The space is O(V + E). On dense graphs, where E is around V^2, the heap version's advantage over the O(V^2) scan shrinks, and implementations sometimes switch; on sparse graphs, the heap version is clearly better.

Edge cases. An empty graph returns 0. A disconnected graph returns −1 because `reached` falls short. A start vertex is arbitrary; the MST total is the same whichever vertex you begin from. Negative edges are handled correctly, as in Kruskal. The `dist = 0` initial entry is a harmless seed, not a real edge, so it contributes nothing to the total.

A variation. Dijkstra and Prim are nearly the same code, and the difference is worth spotting. Dijkstra's heap key is the total distance from the source; Prim's key is the weight of the single edge that reaches the vertex. One accumulates a path cost, the other just takes the cheapest connecting edge. Same priority queue, same loop shape, different meaning of the key — a small change with a large conceptual distance, and a good test of whether you have understood both.

30.9 A Worked Application: Course Schedule

The problem. Given the number of courses and a list of prerequisite pairs [a, b] meaning "b must be taken before a," decide whether it is possible to finish every course. This is LeetCode's "Course Schedule," and it is pure topological sort in disguise.

Picture this. You are planning a degree and some courses list prerequisites. You want to know if there is an order that satisfies everyone. If two courses each require the other — a circular prerequisite — no schedule exists and the answer is no. Otherwise, some order exists, and it is exactly a topological order of the prerequisite graph.

Brute force, then better. The brute force tries every possible order of courses and checks them, factorial. The graph formulation reduces it instantly: build a directed edge from each prerequisite to the course that requires it, then run Kahn's algorithm. The graph is schedulable exactly when the topological sort includes every vertex.

    bool canFinish(i32 numCourses, Vec<Vec<i32>>* prerequisites) {
        Graph g = Graph::new((usize)numCourses);
        for (usize i = 0; i < prerequisites->count(); i += 1) {
            Vec<i32>* pair = prerequisites->atPtr(i);
            i32 course = pair->at(0);
            i32 prereq = pair->at(1);
            g.addDirectedEdge(prereq, course);       // prereq -> course
        }
        Vec<i32> order = Vec<i32>::new();
        return topologicalSort(&g, &order);
    }

The function builds the graph, adding one directed edge per prerequisite in the direction "must come first → depends on it," then delegates entirely to `topologicalSort`, whose boolean return is exactly the answer. `prerequisites->atPtr(i)` returns a pointer to the pair so the inner vector is read without copying. If a cycle exists — two courses requiring each other, or a longer loop — Kahn's algorithm cannot free every vertex, `order` comes up short, and the function returns false.

Time and space. Building the graph is O(V + E), and the topological sort is O(V + E), so the whole thing is O(V + E) time and O(V + E) space, where V is the number of courses and E the number of prerequisite pairs. An exponential problem became linear because the right structure — a directed graph ordering — was recognised.

Edge cases. Zero courses is trivially finishable (empty order, returns true). Zero prerequisites means every course is independent, and every course is emitted immediately. Duplicate prerequisites are harmless; they only add parallel edges and the indegree counts them twice, which still works out. A self-prerequisite (a course requiring itself) is an immediate cycle and returns false.

A variation. The natural follow-up, "Course Schedule II," asks for an actual order, not just yes or no. The answer is the `order` vector Kahn's algorithm already builds; when the function returns true, `order` is a valid schedule, and when false, `order` holds the courses that could be freed before the cycle was hit. This is a recurring pattern — the decision version and the construction version share all their machinery, and the construction just hands you the object the decision ignored.

30.10 A Worked Application: Number of Islands

The problem. Given a 2D grid of '1' (land) and '0' (water), count the islands, where an island is a group of land cells connected horizontally or vertically (not diagonally).

Picture this. A satellite image with land and sea. You want to count the continents. You scan cell by cell; when you hit land you have found a new island, and then you flood the whole island so you never count it again — walking from each land cell to its four neighbours and marking everything reachable. Each flood is one island.

Brute force, then better. The brute force checks every land cell against every other to group them, which is quadratic in the number of cells and easy to get wrong. The graph view makes it linear: each land cell is a vertex connected to its land neighbours, and counting islands is counting connected components — 30.3's problem on a grid, where the neighbours are the four adjacent cells instead of an adjacency list.

    import(lib) std::collections::queue { Queue };

    void exploreDir(Vec<str>* grid, Vec<bool>* visited, Queue<i64>* q, i64 r, i64 c, usize rows, usize cols) {
        if (r < 0 || c < 0) return;
        if ((usize)r >= rows || (usize)c >= cols) return;
        usize flat = (usize)r * cols + (usize)c;
        if (visited->at(flat)) return;
        str row = grid->at((usize)r);
        if (row.at((usize)c) != (u8)'1') return;
        visited->set(flat, true);
        q->enqueue((i64)flat);
    }

    void floodFill(Vec<str>* grid, Vec<bool>* visited, usize sr, usize sc, usize rows, usize cols) {
        Queue<i64> q = Queue<i64>::new();
        visited->set(sr * cols + sc, true);
        q.enqueue((i64)(sr * cols + sc));
        while (!q.isEmpty()) {
            i64 flat = q.dequeue();
            i64 r = flat / (i64)cols;
            i64 c = flat % (i64)cols;
            exploreDir(grid, visited, &q, r - 1, c, rows, cols);
            exploreDir(grid, visited, &q, r + 1, c, rows, cols);
            exploreDir(grid, visited, &q, r, c - 1, rows, cols);
            exploreDir(grid, visited, &q, r, c + 1, rows, cols);
        }
    }

    i32 numIslands(Vec<str>* grid) {
        usize rows = grid->count();
        if (rows == 0) return 0;
        str firstRow = grid->at(0);
        usize cols = firstRow.len;
        Vec<bool> visited = Vec<bool>::new();
        for (usize i = 0; i < rows * cols; i += 1) {
            visited.push(false);
        }
        i32 count = 0;
        for (usize i = 0; i < rows; i += 1) {
            for (usize j = 0; j < cols; j += 1) {
                str row = grid->at(i);
                if (row.at(j) == (u8)'1' && !visited.at(i * cols + j)) {
                    count += 1;
                    floodFill(grid, &visited, i, j, rows, cols);
                }
            }
        }
        return count;
    }

The grid is stored as a `Vec<str>`, one string per row; `str` is a borrowed view, so reading a row never copies the data and never risks the double-free that copying an owning `Vec` would. The `visited` flag is a single flat `Vec<bool>` indexed by `r * cols + c`, which is faster and smaller than a vector of vectors. `floodFill` is BFS from a starting cell: mark it, enqueue it, and repeatedly dequeue a cell and try its four neighbours through `exploreDir`, which bounds-checks, skips visited cells, skips water, and marks and enqueues land. `numIslands` calls `floodFill` once per unvisited land cell, and each call consumes a whole island.

Time and space. Every cell is examined a constant number of times (once by the outer scan, at most four times as a neighbour), so the total time is O(rows × cols), linear in the size of the grid. The visited vector is O(rows × cols), and the BFS queue holds at most that many cells. This is the graph O(V + E) bound with V = cells and E at most 4V, so O(V).

Edge cases. An empty grid returns 0. A grid that is all water returns 0, and the inner condition never fires. A single land cell is one island. Diagonal land does not connect, by the problem's definition; if diagonals counted, four more `exploreDir` calls would be added. A grid whose rows have different lengths would break the flat indexing; the problem guarantees a rectangular grid, and the code assumes it.

A variation. The same flood fill answers "maximum island area" (count the cells the flood consumes and track the maximum), "perimeter of an island" (count exposed cell edges), and "number of closed islands" (an island not touching the border). The graph is identical; only what you do during the flood changes. That is the signature of a well-chosen model: the hard part, the traversal, is shared, and the different questions are small variations on what the traversal records.

1. Comprehension. Explain the difference between an adjacency list and an adjacency matrix in terms of both memory and the cost of the two most common operations: iterating a vertex's neighbours, and testing whether two vertices are adjacent. When is each the better choice?
