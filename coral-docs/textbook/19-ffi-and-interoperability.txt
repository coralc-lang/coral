Chapter 19

Foreign Function Interface and Interoperability

Living With C

Coral is not an island. It runs on operating systems written in C, links against libraries written in C, and must sometimes expose itself to callers written in C. The foreign function interface — the FFI — is the seam where Coral meets everything else, and every systems language has one because every systems language eventually has to call read() and open() and the platform's own functions. Coral's FFI is deliberately thin: declare an extern function with its C signature, call it, and the compiler generates a call that the linker resolves. There is no binding generator to run and no runtime marshalling layer.

Thin does not mean trivial. Crossing the boundary means crossing from Coral's rules — owning types, RAII, checked strings — into C's rules, where a pointer is just an address and a string is just bytes until a nul. This chapter teaches the mechanism and, more importantly, the discipline: how to declare foreign functions, how to pass and receive data across the boundary, how to represent C's types, and how to build a correct wrapper so that the rest of your program never touches the raw interface.

19.1 Declaring an Extern Function

An extern function is declared with the extern keyword and a body-less signature:

    pub extern i64 read(i32 fd, cchar* buf, u64 count);
    pub extern i32 open(const cchar* path, i32 flags, i32 mode);
    pub extern void free(rawptr ptr);

That is the entire declaration. There is no parameter-name requirement — signatures may be written with unnamed parameters, `i32 open(const cchar*, i32, i32)` — and no need to specify a library for the common ones, because the C standard library is linked by default. A function in a library that needs an explicit link, such as the math library, is declared the same way and the build provides the flag:

    // links against -lm
    pub extern f64 sqrt(f64 x);
    pub extern f64 pow(f64 x, f64 y);

The declaration's job is to tell the compiler the calling convention and the types. For the default C convention, extern alone is enough. When a function uses a non-default convention, the convention is named:

    pub extern("C") void callback_handler(i32 code);

extern("C") makes the C convention explicit, which matters where a platform could default differently. The default with no qualifier is the platform's C convention, so the two are usually the same; writing it out is a clarity improvement more than a behavioural one on mainstream targets.

The standard library's own platform bindings are the model to read. The platform module holds libc for POSIX systems and win32 for Windows, and each is a list of extern declarations with no bodies. This is how Coral reaches the operating system, and it is how you would add a binding the library does not yet have:

    // a fragment of platform/libc.crl
    pub extern i32 getcchar();
    pub extern i32 putcchar(i32 c);
    pub extern u64 strlen(const cchar* s);
    pub extern rawptr malloc(u64 size);
    pub extern rawptr mmap(rawptr addr, u64 length, i32 prot, i32 flags, i32 fd, i64 offset);

A function with no body and the extern modifier is a promise to the linker: there is a symbol with this name and this signature, and it will be resolved at link time. If the symbol does not exist, the link fails, which is the correct and early way to discover a typo in a binding.

19.2 C Types and Coral Types

The boundary has a small translation table, and knowing it prevents the most common FFI bug, which is a type that is the right size on one platform and the wrong size on another.

    C type        Coral type       note
    int           i32              on the platforms Coral targets
    long          i64 (LP64)       i32 on Windows (LLP64) — check the platform
    unsigned      u32
    size_t        usize            pointer-sized
    char          cchar            a byte, signedness platform-dependent
    char*         cchar*           a C string or byte buffer
    const char*   const cchar*     a read-only C string
    void*         rawptr           an untyped pointer
    struct foo    struct foo       by value, with a matching layout
    function ptr  void(rawptr)     the same, spelled Coral's way

Three of these are worth dwelling on. cchar is the C char: a single byte with platform-dependent signedness, and the element type of a C string. It is deliberately distinct from the Coral char, which is a Unicode codepoint, and from u8, which is unambiguously unsigned. Using cchar at the boundary is a signal that you are dealing with C's notion of a character. rawptr is the void pointer: it carries an address and no type, and converting to and from it is explicit. And usize is size_t: the pointer-sized unsigned integer, which is the type of every C length and count.

A function pointer crosses the boundary as a Coral function-pointer type. A C function that takes a callback takes a parameter of the form RetType(params):

    pub extern void qsort(rawptr base, usize count, usize size, i32(const rawptr, const rawptr) cmp);
    pub extern rawptr signal(i32 signum, void(i32) handler);

And Coral can pass a function to it, because a Coral function whose signature matches the function-pointer type is usable as that type. The one subtlety is the calling convention: a callback invoked by C must use the C convention, so a Coral function passed across the boundary must have a C-compatible signature, which is to say it must take and return only FFI-compatible types, not owned Coral types with drop behaviour.

19.3 C Strings and Coral Strings

The single largest source of FFI bugs is string handling, and Coral attacks it by making the two representations distinct types. A Coral str is a pointer and a length. A C string is a pointer to nul-terminated bytes with no length. They are not interchangeable, and the language does not pretend they are.

To call a C function that wants a C string, you must have a C string. A literal with the C prefix is one:

    open(C"/etc/hosts", 0, 0);

The C"..." literal is nul-terminated in memory and has type const cchar*, so it can be passed directly. For a runtime string — a String or a str — you convert explicitly. A String can produce a C string view when it has been allocated with a trailing nul, and a str can be copied into a buffer with one:

    String s = String::from("filename.txt");
    cchar* cstr = s.asCstr();

    // from a view that must be copied
    String tmp = String::from(view);
    open(tmp.asCstr(), 0, 0);

The conversion is not free and it is not implicit, and that is the point: converting a length-carrying string to a nul-terminated one is a decision with a cost, and the API makes you write it. The reverse direction is equally explicit: fromCstr turns a C string back into a Coral string by measuring its length.

    String owned = String::fromCstr(cstr);
    str view = str::fromCstr(cstr);       // borrows; strlen to find the length

Two warnings belong here. First, a borrowed str made from a C string does not own the bytes — if the C code frees them, the view dangles. Second, a str that is not nul-terminated must not be passed to a C function expecting a C string; the function will read past the end looking for a nul that is not there. The types make the distinction visible, but they cannot make it impossible, because at the boundary the C function's expectation is not something Coral can see.

19.4 Passing Structures and Buffers

A Coral struct can be passed to C by pointer, or by value if its layout matches. Matching layout is the catch. By default the compiler is free to reorder and pad fields for efficiency, which means a plain Coral struct does not necessarily have the layout C expects. For a struct that must cross the boundary, the layout is pinned with attributes:

    #[[packed]]
    struct Header {
        u8  version;
        u8  flags;
        u16 length;
        u32 checksum;
    }

    pub extern i32 readHeader(i32 fd, Header* out);

#[[packed]] removes the padding the compiler would insert, so the struct's size is the sum of its fields and its bytes lie in the declared order. This is required for wire formats, protocol headers, and any ABI where the byte layout is specified. The trade-off is performance: a packed struct may be slower to access because unaligned fields cost more on some platforms. The rule is to pack exactly the structs that cross a boundary and leave in-memory types unpacked.

#[[reorder]] is the opposite permission: it tells the compiler it may permute fields for a tighter layout, which is fine for a private in-memory type and wrong for anything that crosses the boundary. A struct that is neither packed nor reordered has a layout the compiler chooses, and that layout must be treated as private. The discipline is simple and worth chiselling: if a struct crosses the FFI, mark it packed; if it does not, treat its layout as nobody's business.

Buffers cross as pointers with an explicit length. A C function that fills a buffer takes a rawptr and a usize:

    u8 buffer[4096];
    i64 n = read(fd, (cchar*)buffer, 4096);

The cast from the array to cchar* is a cast to the parameter's type; the length is passed separately because C has no way to infer it. The caller owns the buffer and its lifetime; the C function writes into it and returns how many bytes it used. This pattern — a caller-provided buffer and a returned count — is the standard shape of every C read, and wrapping it so that callers get a String or a Vec back is the job of a wrapper.

19.5 Wrapping the Boundary

The interface a C library presents is designed for C, which is to say it is full of raw pointers, integer return codes, and out-parameters, and it does not use Coral's types. Do not let that interface leak into your program. Write a wrapper — a small Coral module that does the conversions, checks the return codes, turns them into Results, and exposes a Coral-shaped API. The rest of the program then uses the wrapper and never sees a rawptr.

A wrapper for a C file API shows the shape. Suppose the C side offers:

    pub extern rawptr fopen(const cchar* path, const cchar* mode);
    pub extern u64 fread(rawptr ptr, u64 size, u64 count, rawptr stream);
    pub extern i32 fclose(rawptr stream);

Wrap it in an owned type with a drop, and a Result-returning open:

    import(lib) platform::libc { fopen, fread, fclose };

    pub struct File {
        rawptr handle;
    }

    pub variant FileError {
        NotFound { String path; },
        PermissionDenied { String path; },
        Unknown { i32 code; },
    }

    pub extend File {
        void drop() { fclose(self.handle); }
    }

    pub Result<File, FileError> fileOpen(str path) {
        String tmp = String::from(path);
        rawptr h = fopen(tmp.asCstr(), C"r");
        if (h == null) {
            return FileError::NotFound { .path = path.clone() };
        }
        return File { .handle = h };
    }

    pub Result<usize, FileError> fileRead(File* f, u8[] buf) {
        u64 n = fread((rawptr)buf.ptr, 1, buf.len, f->handle);
        return (usize)n;
    }

Everything that made the C API awkward is hidden here. fopen's null-on-failure becomes a Result with a typed error. The rawptr handle is wrapped in a struct that owns it and frees it through @drop, so a File going out of scope closes the descriptor — RAII at the boundary, which is the single most valuable thing a wrapper provides. The C string conversion is done once, inside. Callers write fileOpen("config.txt") and get a Result, and they never hold a rawptr or remember to close.

The wrapper is also where the ownership contract is decided. The File owns the handle, so copying a File would double-close it; the wrapper should either forbid copying or use the handle the way a file descriptor is meant to be used, shared by value with a reference count. The language does not decide this for you, because C does not. The wrapper's job is to make the decision once, in one place, and to express it in the type so that the rest of the program inherits it.

19.6 Calling Into Coral From C

The direction also matters: sometimes a Coral function must be callable from C — an entry point, a callback registered with a C library, a symbol in a shared object. A Coral function is callable from C when its signature is FFI-compatible and its name is exported. The no_mangle attribute keeps the function's name unmangled so the linker symbol matches what C expects:

    #[[no_mangle]]
    pub extern("C") i32 coral_entry(i32 argc, cchar** argv) {
        return main(argc, argv);
    }

The extern("C") on a definition asserts the C calling convention; no_mangle keeps the symbol name. Together they make coral_entry visible to a linker and callable from C by that name. A Coral function registered as a callback needs no attributes beyond the C-compatible signature the function-pointer parameter already demands. And a Coral function passed to C must not assume it can throw, panic, or unwind across the boundary in a way C cannot handle; errors must be communicated through return values, exactly as C expects.

A @drop type must not be passed by value to C, full stop, because C has no mechanism to run the destructor. Such a type may cross by pointer, with the ownership contract the wrapper declares, but never by value. The compiler's knowledge of drop is a Coral-side discipline; the moment a value's bytes leave for C, that discipline does not travel with it.

19.7 A Worked Example: Reading a File Through a Wrapper

Assemble the pieces into a program that reads a text file through the wrapper of 19.5, keeping the mess in one module.

    import(lib) std::io::ios { println, eprintln };
    import(lib) std::text::string { String };
    import(lib) std::collections::vec { Vec };

    Result<String, FileError> readWholeFile(str path) {
        Result<File, FileError> opened = fileOpen(path);
        switch (opened) {
            Err { error } => return error,
            else          => {}
        }
        File f = opened.unwrap();

        String out = String::new();
        u8 buf[4096];
        Result<usize, FileError> r = fileRead(&f, buf[..]);
        while (r.isOk()) {
            usize n = r.unwrap();
            if (n == 0) break;
            out.pushView(str::fromParts(buf, n));
            r = fileRead(&f, buf[..]);
        }
        return out;
    }

    i32 main() {
        switch (readWholeFile("config.txt")) {
            Ok { value }  => println("read {} bytes", value.len),
            Err { error } => eprintln("could not read file"),
        }
        return 0;
    }

main never sees a rawptr, a cchar, or a return code. It sees a Result and a String, because readWholeFile turned C's fopen/fread/fclose world into Coral's Option-and-Result world and hid the difference. The f in readWholeFile is owned, so it is closed automatically when the function returns — success or failure, the descriptor is released. The buffer is a fixed array, borrowed as a slice buf[..] and passed down as a pointer and length, converted by the wrapper. This is what a good FFI looks like from the outside: the boundary is invisible, and the discipline of the boundary is contained in one wrapper rather than scattered across the program.

19.8 Exercises

1. Comprehension. Write the Coral signature for a C function `double clamp(double x, double lo, double hi);` and for one returning `char*`.

2. Comprehension. What is the difference between Coral's char, cchar, and u8? Which crosses to C as a C char?

3. Implementation. Declare externs for the C functions getpid, time, and getenv, and write a program that prints the process id and the value of an environment variable.

4. Strings. Write a function that takes a str and calls strlen on its C equivalent. Why must you convert first, and what happens if you pass a non-nul-terminated view?

5. Layout. Define a packed struct matching this C declaration, and assert its size: `struct { char tag; int value; }`.

6. Drop. Write a wrapper for a C resource (a lock, a handle, or a buffer) whose destructor frees it. Show a function that uses it and explain when the destructor runs.

7. Errors. A C function returns -1 on failure and sets errno. Wrap it in a Coral function returning a Result, and explain how you get at errno.

8. Callbacks. Declare a C function that takes a callback invoked on each element of an array. Write the Coral callback and pass it.

9. Export. Write a Coral function with the C calling convention and an unmangled name that C could call. Why does a @drop type not belong in its signature?

10. Design. Take a C library you know — zlib, sqlite, a graphics library — and design its wrapper: which types become Coral structs, which functions return Results, and where do the destructors go?

11. Meta. The chapter argues every FFI should be wrapped. Argue for the opposite: a case where a program should call C directly rather than build a wrapper. What makes the wrapper not worth its cost?
