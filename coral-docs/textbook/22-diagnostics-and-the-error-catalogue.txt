Chapter 22

Diagnostics and the Error Catalogue

A Compiler's Second Job

A compiler has two jobs. The first is to translate correct programs. The second, and the one that determines whether the first is usable, is to explain incorrect ones. A diagnostic is not a failure message; it is a piece of writing whose reader is a person who has just made a mistake and wants to know what it was and how to fix it. Getting that wrong is expensive. A vague error sends a programmer on a search; a good one ends the search in ten seconds. Coral's diagnostics are organised around this idea, and the organisation shows in two things: every diagnostic carries a stable code, and every code has a defined audience, from a lexical typo to a subtle lifetime violation.

This chapter is a tour of the catalogue. It is organised by what kind of mistake each range catches, with a worked example of the shape each one takes. It also covers how the compiler is invoked to surface them, and what makes a diagnostic good — because the conventions here are part of the language, not an implementation detail, and code that reads well is code whose mistakes read well too.

22.1 How Diagnostics Are Invoked

The compiler surfaces diagnostics through three flags and one subcommand.

The default build reports errors and a core set of warnings. --strict promotes warnings to errors, which is the setting a release build should use so that nothing questionable ships. --warn-unused enables the unused-variable, unused-import, and unused-parameter checks, which are off by default to avoid drowning a new project in noise but which a mature project turns on. --explain CODE prints a longer explanation of a single code, the way a man page explains a command:

    $ coralc --explain E0608

The build subcommands compose with these; a project that wants strict checking sets the flags in the build file so that every build, and every developer, gets the same standard. That consistency is the point — a lint that is on for one developer and off for another is worse than a lint that is off everywhere, because the codebase drifts toward whatever the least-strict configuration allows.

22.2 What Makes a Diagnostic Good

The conventions for a Coral diagnostic are worth stating, because they are checkable.

A diagnostic names the problem in a sentence a person would say. Not "invalid token" but "identifier contains a non-ASCII lookalike character (U+0430) that mimics ASCII 'a' (U+0061)." The second sentence tells the reader what happened, where, and why it is a problem; the first makes them guess.

A diagnostic points at a location, and when it can, at the related location too. A non-exhaustive switch points at the switch and names the missing case. A signature mismatch points at both the trait's declaration and the implementation. The extra location is often the difference between "there is an error somewhere" and "these two things disagree."

A diagnostic carries a code, and the code is stable. A code can be searched, discussed in a review, added to a list of ignored warnings, and used to find the same class of mistake elsewhere. A message without a code cannot be referenced; a message with one becomes a shared vocabulary. The code is not the whole message — a code without a sentence is not a diagnostic — but a sentence without a code is not referenceable.

A diagnostic suggests a fix when the fix is mechanical. An unknown attribute suggests the nearest known attribute by edit distance. An unknown format specifier suggests the closest specifier. A typo in a function name suggests the function that was probably meant. A suggestion is worth a paragraph of explanation because it converts a diagnostic from a puzzle into an edit.

And a diagnostic generated by user code — a @compileError, or a format-string mismatch raised inside a comptime block — must be structured like any other. It should not be a debug string like `evalComptimeBody FAILED decl=4106`. A compile-time error raised by library code is still read by a person, and it should carry a code, a location, and a sentence. This is a commitment the compiler makes to itself: it may not have two classes of diagnostic, one for its own mistakes and one, uglier, for the ones it surfaces on behalf of a library. If the format machinery detects that a print has more placeholders than arguments, that is a formatted diagnostic with a location, not a debug line. The catalogue is uniform, and the uniformity is what makes it learnable.

22.3 E01xx — Lexical and Parse-Time

The E01xx range catches problems visible at the texture of the source: characters that are not what they look like, and annotations in the wrong place.

E0103, Unicode homoglyph confusable reference, is the flagship of the range and the model for the rest. A programmer pastes an identifier that contains a Cyrillic а (U+0430) where an ASCII a (U+0061) was meant. Both glyphs render identically; only the byte values differ. A naive compiler reports "undeclared identifier," which sends the reader hunting for a scope bug that does not exist. Coral reports the actual problem, by codepoint:

    // error E0103: identifier `cаche` contains a non-ASCII lookalike
    //   character (U+0430 CYRILLIC SMALL LETTER A) that mimics ASCII 'a' (U+0061)

The message names the character, its codepoint, and the ASCII character it imitates, which is exactly what the reader needs to fix it in one edit. This is the standard the whole catalogue aims for.

E0104, misplaced attribute target, fires when an attribute like #[[inline]] is attached to a statement or expression where it has no meaning, rather than to a declaration. The compiler knows which attributes are valid at which positions and reports the mismatch. E0105, doc-comment on an expression statement, fires when a documentation comment is attached to an arbitrary line of code inside a block rather than to a structural declaration, which usually means the comment was meant for something else.

22.4 E02xx — Type Layout

The E02xx range concerns how values occupy memory, and its most important member is the one that stops a program from being impossible.

E0201, cyclic type layout of infinite size, catches a struct that contains itself directly, with no indirection:

    struct Node {
        i32 data;
        Node next;      // error E0201: Node contains itself
    }

The compiler cannot compute Node's size because Node's size depends on Node's size. The fix is an indirection — a Node* next, or a boxed pointer — which makes the size finite because a pointer's size is known. The message explains the cycle and names the field that closes it. This is not merely a limitation; it is the compiler refusing to emit a type that has no bytes.

E0202 catches a zero-sized field used in a position that forces it to overlap adjacent data; E0203 catches a representation that conflicts with the target's alignment rules; E0204 catches bitfields that exceed their backing storage; E0205 catches an attempt to cast a composite type directly to a primitive without an explicit serialisation pattern. Each is a layout question, and each is answered at compile time rather than at a crash.

22.5 E03xx — Constant Evaluation

The E03xx range catches mistakes the compiler can see because they happen during constant evaluation, whether in a comptime block or in a const initialiser.

E0305, division by zero in constant evaluation, fires when constant code divides by a literal zero — the compiler catches at build time what would be a crash at runtime. E0306, integer literal overflows declared type, fires when a literal fits no value of its declared type:

    u8 x = 300;      // error E0306: 300 does not fit in u8

E0307, constant array index out of bounds, fires when a fixed-size array is indexed with a constant that is outside its bounds:

    i32 a[4];
    a[7] = 1;        // error E0307: index 7 out of bounds for [4]

This is the compile-time half of the bounds-safety story. A constant index into a fixed array is checked at build time, so the corresponding runtime check disappears for the common case where the index is known. E0304, dereferencing a raw pointer inside constant evaluation, catches a comptime block attempting to read a hardware address, which is not deterministic and so cannot be part of a constant. Each of these errors is a program that would have misbehaved, caught before it ran.

22.6 E04xx — Inline Assembly

The E04xx range guards hand-written assembly, where the compiler's model of the machine must match the programmer's. E0401 catches an output bound to a register class whose size does not match the variable — asking for a 64-bit value in a 32-bit register. E0402 catches a register listed as clobbered while also passed as a live input or output, which is a contradiction. E0403 catches a volatile write immediately overwritten by a non-volatile read, which is a race the programmer probably did not intend. Assembly is the deepest end of the language, and these checks exist because the mistakes there are silent and catastrophic.

22.7 E05xx and the Build Diagnostics — Linking and Modules

The E05xx range catches problems at the boundary between Coral and the linker or among modules. E0501 catches a symbol that conflicts with a reserved ABI name. E0502 catches a cyclic module initialisation chain, where module A's startup depends on B's and B's on A's. E0503 catches a function pointer passed to an external API that demands a different calling convention.

Module resolution produces its own build-time diagnostics, distinct from the source-level catalogue because they are the builder's findings rather than the compiler's. An unresolved re-export, a missing module, a duplicate module identity, an alias pointing at a nonexistent module, an unresolved module import, and a cycle in the module graph are each reported with a code and, for a cycle, with the trace that shows the loop. These are the diagnostics of Chapter 20's pipeline: the builder reads the module surfaces and the source imports, and anything it cannot resolve is a build error rather than a compiler crash. The value of separating them from the source-level codes is that "your imports do not resolve" and "your code has a type error" are different problems with different fixes, and the catalogue keeps them distinguishable.

22.8 E06xx — Control Flow, Switch, and Data Flow

The E06xx range is the largest and the most frequently met, because it catches the mistakes a program makes about its own control flow.

E0608, switch not exhaustive and missing else, is the one the earlier chapters promised. A switch over an enum or variant that lists some cases, has no else, and does not cover every case is an error:

    switch (shape) {
        Shape::Circle { r } => area = pi * r * r,
        // error E0608: non-exhaustive switch; missing Shape::Square, Shape::Point
    }

The message names the missing cases, so the fix is immediate. This single diagnostic is why the variant-and-switch style of Chapter 13 is safe: forgetting a case is not a silently wrong program but a build failure with a list. E0609, unreachable switch case, catches a duplicate case value or a variant already covered by an earlier arm — the compiler's way of saying "this arm can never run, you probably meant something else." E0610, fallthrough attribute on last arm, catches a leftover #[[fallthrough]] at the end of a switch.

The rest of the range concerns data flow. E0601 catches a branch that reaches the end of a non-void block without yielding a value, when other paths do yield. E0602 catches use of partially moved or deallocated memory — passing a struct to a function that consumes it, then reading one of its fields. E0603 catches unreachable code after a diverging statement; E0604 catches a non-void function that can fall off its end without returning; E0606 catches a self-assignment that has no effect; E0607 catches a local used before every path has initialised it. Each of these is a class of bug that has shipped in every language that lacked the check, and Coral's position is that the compiler can see them, so it should.

22.9 E07xx — Parse Ambiguities

The E07xx range is unusual and worth understanding, because it is about grammar rather than semantics: it catches places where a piece of C-like syntax has two readings and the compiler must choose one.

E0701 is the classic most-vexing-parse. The code Time Keeper(Timer()); can read as either a function call or a variable declaration, and a recursive-descent parser must pick one. Coral picks one and tells the programmer exactly how it resolved the ambiguity, rather than leaving them to discover it later. E0702 catches a dependent-scope name that could be a type or a value without a hint, flagging the assumption the parser made. E0703 is a safety valve: if a malformed expression forces speculative parsing down too many branches without a synchronising token, the parser kills the branch rather than overflowing its stack, and reports that it did. E0704 is the dangling else, where a nested if without braces binds the else to the innermost condition, and the compiler reports the binding it chose so the programmer can add braces if that was not the intent.

This range is the compiler being honest about its choices. Silent disambiguation is where languages acquire their reputations for surprising behaviour; stating the resolution is where they lose it.

22.10 E08xx — Lints

The E08xx range is the advisory family: things that are legal but almost certainly not what was meant. They are warnings by default and errors under --strict.

E0801, unused variable, is the one people meet first, and the one they appreciate after the first time it catches a real mistake. E0802, unused import, keeps a file's dependency list honest. E0803, unused parameter, catches a parameter never read in the body — the convention is that a leading underscore opts out, for the callback whose signature requires an argument it does not use. E0804, binding never mutated but declared mutable, catches a var that could have been const, which is a small but real clarity gain. E0805, use of deprecated item, is generated by the #[[deprecated]] attribute and names the replacement.

E0806 and E0807 are the attribute lints from Chapter 21. An unknown attribute name is reported with a nearest-match suggestion, so a typo becomes a fix rather than a silent no-op. A duplicate attribute is reported so that a repeated or contradictory instruction is never quietly dropped. These two matter more than their size suggests, because attributes are how a programmer tells the compiler what they intend, and a dropped instruction is a divergence between intent and result.

22.11 E09xx — Format Strings

The E09xx range checks the format strings of Chapter 17, and it exists because the compiler can see both the format and the arguments.

E0901, format string argument count mismatch, fires when the number of placeholders does not match the number of arguments: `println("{} {}", a)` is one argument short. E0902, format placeholder type mismatch, fires when a specifier demands an integer and receives a type with no such rendering. E0903, unknown format specifier, fires on a specifier outside the set, with the closest known specifier suggested:

    println("{q}", value);    // error E0903: unknown specifier `q`; did you mean `{}`?

This range is the payoff of the comptime machinery: because the format string and the arguments are both visible at compile time, a class of error that is a runtime crash in C and a runtime surprise in many dynamic languages is a build failure in Coral. The trade, as Chapter 17 noted, is that a format string built at runtime cannot be checked; but the overwhelming majority of format strings are literals, and for those the check is free.

22.12 E10xx — Const and Mutation

The E10xx range catches mutation of things that must not change. E1001, mutation through a const-qualified pointer, fires when a function takes a const T* and writes through the pointee:

    void overwrite(const i32* p) {
        *p = 0;      // error E1001: cannot mutate through const i32*
    }

This is const's teeth. The promise a const parameter makes to its caller is that the pointed-to value will not change; a violation of the promise is a bug in the callee, and the compiler catches it at the store rather than at the caller's surprise. It is a member of the same family as the const method check, and the two together are what make const worth writing.

22.13 E11xx — Compile-Time Execution

The E11xx range guards the comptime machinery of Chapter 7, where code runs during the build. E1101 catches a comptime block that reads or stores an address only known when the binary is loaded — a heap allocation or a thread-local — which cannot be a compile-time constant. E1102 catches a comptime write to a global constant or a frozen read-only segment. E1103 is the tripwire: a comptime loop or recursion running without bound is cut off, with the macro call-stack depth shown, so an accidental infinite loop in a type generator is a diagnostic rather than a compiler hang. Its counterpart, the unbounded-comptime case, is why a comptime block is not simply "run the interpreter forever"; it has a budget, and exceeding it is reported. E1104 catches a generic type factory that returns a runtime-constructed instance where a concrete type token was required.

22.14 E12xx — Methods and Traits

The E12xx range checks the trait machinery of Chapter 6. E1201, overlapping method definitions across blocks, catches a method defined twice for the same type across different extend blocks — the method blocks may be separate, but a signature may be defined only once. E1202, trait method signature mismatch, catches an implementation whose method does not match the trait's declaration in parameters or return type. E1203, missing required trait method, catches a type that claims a trait implementation but does not supply a required method, which in a language with abstract types would be "cannot instantiate abstract class." Together these three make a trait conformance trustworthy: a type that says it implements Shape either does, or does not compile.

22.15 E13xx — Drop and Bounds

The final range guards the interaction of ownership with traits and generics, and it is the most subtle family in the catalogue.

E1301, explicit call to a drop method disallowed, catches a programmer writing x.drop(). Because drop is driven by scope termination, calling it explicitly invites a double free when the value's scope also ends. The compiler blocks the manual call and points at the automatic mechanism. This is the counterpart to the no_drop attributes: when you want manual cleanup, you use the attributes and a normal cleanup function; when you want automatic cleanup, you let the scope end the value's life. What you may not do is both. E1302 catches a drop implementation on a type whose size varies entirely with comptime conditions, where a fixed-layout destructor cannot be sound. E1303 catches a field moved out of a struct before the struct's drop runs, which would let drop execute on partially uninitialised memory. E1304 catches a generic function that passes a type to a context requiring a capability without declaring the bound — passing a T to something needing a serialisable type without stating T : Serializable.

Each of these four is a lifetime or capability mistake that a systems language must catch to be sound, and each is caught at compile time with a location and a sentence. They are the deepest part of the catalogue, and a reader who understands why each fires understands the language's ownership model.

22.16 A Worked Example: Reading a Diagnostic Trail

A single mistake often produces several diagnostics, and the skill of reading them in order is worth practising. Consider a function with a non-exhaustive switch inside a non-void function, with an unused variable above it:

    str label(Shape s) {
        i32 unused = 0;
        switch (s) {
            Shape::Circle { r } => return "circle",
        }
    }

The compiler reports, in order. First E0801: unused variable `unused`. Next E0608: non-exhaustive switch over Shape, missing Shape::Square and Shape::Point. Then, because the switch may not return on every path, E0604: non-void function `label` can reach its end without returning. Three diagnostics, one root cause in two places: a forgotten unused variable and a switch that is not total. Adding the missing cases makes the function total, which makes E0604 disappear, and removing the unused variable clears E0801. The order matters because E0604 is a consequence of E0608; fixing the missing cases fixes both, and a reader who understands the dependency fixes the cause rather than chasing the symptom.

The worked example shows why stable codes are worth the trouble. A message like "control reaches end of non-void function" and a code E0604 are the same finding, and the code lets a reader search for the pattern, add a consistent suppression, or find the reference in this chapter. The catalogue is not a list of strings; it is the compiler's vocabulary, and the vocabulary is part of the language.

22.17 Exercises

1. Comprehension. Why does every diagnostic carry a code? Give two things a code makes possible that a bare message does not.

2. Comprehension. E0201 prevents a type of infinite size. Explain why a pointer breaks the cycle, and give a self-referential type that is legal.

3. Implementation. Write a program that triggers E0608, then fix it three ways: add the missing arms, add an else, and add a fallthrough. Which fix is right, and when?

4. Implementation. Trigger E0307 with a constant index and with a runtime index. Which fires at compile time, and which does not?

5. Lints. Turn on --warn-unused and count the warnings in a program of yours. Fix them. Which warned about a real bug and which were noise?

6. Format. Write three calls that trigger E0901, E0902, and E0903. Then write the corrected calls.

7. Traits. Trigger E1203 by declaring a trait conformance and omitting a method. What does the diagnostic name, and what is the fix?

8. Drop. Trigger E1301 by calling drop directly. What does the compiler suggest instead, and why is the manual call unsafe?

9. Ordering. Write a program with a missing switch case inside a non-void function. List the diagnostics in order and identify which are causes and which are consequences.

10. Meta. The catalogue is organised by mistake kind rather than by compiler pass. Argue for and against this. Would you group E06xx differently, and why?

11. Writing. Take E0701, the most-vexing-parse diagnostic, and write the message you think it should produce for the example Time Keeper(Timer());. Aim for the standard of E0103: what happened, where, and why.
