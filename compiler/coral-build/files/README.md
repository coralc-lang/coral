# crlbc — a lexer + parser for the `.crlb` format (v2, rewritten)

A hand-written, zero-allocation-lexer, no-template C++ lexer and
recursive-descent parser for the full v2 `.crlb` grammar (the "Full .crlb
grammar (v2)" write-up: the original grammar plus `schema`, `strict`,
`workspace`, `profile`/`extends`, `target`/`link`/`artifact`, `features`,
`env`, `phase`, `hook`, `test`/`bench`, `log`/`metrics`,
`lint`/`format`/`lsp`, `ci`, `remote`, `deps`).

This is a rewrite of an earlier version, done to fix a real performance bug
and tighten up the style rules it's built under. If you're comparing the
two: this one is faster, has no templates, and calls things as methods
(`self->parseValue()`) instead of free functions taking a pointer
(`parse_value(p)`).

## Build & run

```sh
g++ -std=c++17 -Wall -Wextra -O2 -o crlbc \
    arena.cpp str.cpp lexer.cpp ast.cpp parser.cpp main.cpp
./crlbc example.crlb        # parses a file and dumps the AST
./crlbc                     # no args: parses a small embedded demo string
```

`example.crlb` is the full canonical v2 example from the spec, verbatim.
Verified: builds warning-free under `-Wall -Wextra`, passes clean under
`-fsanitize=address,undefined`, and parses the full example plus a battery
of edge cases (escapes, nested/empty/trailing-comma lists, both error
paths) correctly. A stress file with 20,000 real string-valued fields
parses in ~9ms — see "Why the lexer allocates nothing" below for why that
number matters.

## The rules this was rewritten under

**No templates.** `DynArray<T>` is gone. `dynarray.h` instead defines a
macro, `DEFINE_ARRAY(Name, Elem)`, that expands to an ordinary struct with
ordinary methods — one concrete array type per element type
(`FieldArray`, `ChildArray`, `ValueArray`), generated by text substitution
at the preprocessor, not by the compiler instantiating a class template.
This costs three lines of macro invocation instead of one `template`
declaration, at the price of every array type being a real, distinct,
non-generic struct — which is the actual ask.

**Real methods, not `free_func(&obj, ...)`.** Everything that used to be
`lexer_next(&lx)` / `parse_value(p)` / `arena_alloc(&arena, size, align)`
is now a method: `lexer.next()`, `self->parseValue()`, `self->arena->alloc(...)`.
No function anywhere takes "the object it operates on" as an explicit
pointer parameter; that's what `this` is for. (Ordinary value parameters —
`Node::addField(Str name, Value v)`, `AstDumper::dumpNode(Node* n, i32
depth)` — are unaffected; the rule is specifically about not re-deriving
method-call syntax by hand.)

**`self` is `this`.** `types.h` defines `#define self (this)`, and every
method body says `self->field` / `self->method()` instead of relying on
implicit `this->`. It's the exact same pointer; it's there for the
"self"-flavored reading, not for any behavioral difference.

**Sized integer types, spelled the requested way.** `types.h` defines
`u8/u16/u32/u64` and `i8/i16/i32/i64` and `f32/f64` as plain `typedef`s
over the built-in types (not `uint8_t`/`stdint.h`). Lengths, offsets, and
counts throughout the codebase are `i64`; raw bytes in the arena are `u8`.

**Union, used for real this time.** `Value` (the STRING/NUMBER/BOOL/LIST
value type) is a genuine C++ `union` now, not four separate fields living
side by side. `Str`, `i64`, `bool`, and `ValueArray*` are all trivial
types, so the union itself is trivially copyable — no constructors,
destructors, or manual lifetime management needed. `Str` in particular has
no user-declared constructors specifically so it stays trivial and can sit
inside that union without complication; it's built via `Str::make(...)` /
`Str::fromCstr(...)` static methods instead.

## Why the lexer allocates nothing

The earlier version called into an arena allocator once per *string
token*, sized to `remaining-length-of-the-file`, every single time —
i.e. real allocation work per string, sized to how much of the file was
left, not to the string itself. For a file with many string literals late
in it, that's `O(file_size)` work per string, so `O(n²)` overall. That's
not a style nit, it's an actual bug, and it matters here specifically
because this is meant to be a build tool's front end, re-run on every
invocation.

The rewrite does none of that:

- Identifiers, numbers, and punctuation were already, and still are,
  zero-copy: a `Str` is just `{ptr, len}` pointing straight into the
  source buffer.
- An unescaped string literal (the overwhelming common case) is *also*
  zero-copy: same trick, a slice of the source between the quotes.
- A string literal that *does* contain an escape (`\n`, `\"`, ...) is
  decoded **in place**: resolving an escape only ever shortens the text,
  so the decoder can write the resolved bytes back over the same span
  it's reading from, with the write cursor always at-or-behind the read
  cursor. This needs the source buffer to be mutable (`char* src`, not
  `const char*`), which is why `main.cpp` loads the file into an owned,
  writable heap buffer.

Net effect: the lexer (`lexer.h`/`lexer.cpp`) doesn't hold a reference to
an `Arena` at all — it has nothing to allocate from, because it never
allocates. The `Arena` in `arena.h` is used exactly where you'd expect an
arena to earn its keep: building the AST (`Node`s and the three
`DEFINE_ARRAY` types), where the tree's lifetime genuinely outlives the
scan that built it.

## Design: one generic `Node`, not ~25 bespoke structs

The grammar has ~15 top-level declaration kinds and ~10 block kinds, but
almost all of them reduce to the same shape: an optional string label, an
optional `extends` target, and a body that's a mix of `IDENT = value ;`
fields and a handful of nested blocks. Rather than one struct per
declaration, the parser builds a single generic `Node` (`ast.h`) tagged
with a `NodeKind`, with generic `Field` entries for every
`IDENT = value ;`-shaped construct — that covers plain fields, `modules`/
`skip`, `provides`/`requires`/`exclude`/`include`/`features` inside
`override`, `feature_decl` entries, `env` pairs, `doc` fields, and
`dep_field` entries, since they're all structurally identical. This
mirrors the spec's own stated philosophy that the parser accepts more
than is semantically valid and leaves enforcement to "the builder" (e.g.
the spec notes `phase` needs `on`/`run` but "the parser doesn't" enforce
that, and `deps`/`remote` are "parsed but not evaluated").

## Two things flagged in the grammar text itself

Implementing this against the exact EBNF surfaced two inconsistencies
between the grammar and its own canonical example — both resolved by
following the example:

1. `top_decl` doesn't list `phase_decl`, `lint_decl`, or a bare top-level
   `override_block`, but the canonical v2 example uses all three at the
   top level (`phase "lex" { ... }`, `lint { ... }`, and
   `override "coral-lexer" { ... }` outside any `build`). This parser
   accepts all three there.
2. `field = IDENT "=" value ";"` requires a trailing `;`, matching the v2
   example throughout — but the *original* (pre-v2) example omits
   semicolons after plain fields even though it's governed by the same
   production. This parser follows the EBNF (and the v2 example) and
   requires the `;`.

## The one real grammar ambiguity: `target`

`target` is both a reserved plain field (`target = "native-x86_64";`) and
the v2 block keyword (`target "corald" { ... }`) — the canonical example
uses both in the same `build`. Resolved with one token of lookahead: if
what follows `target` is `=`, it's the field; otherwise (a `STRING` or
`{`) it's the block. The same lookahead also disambiguates `env`
(`env = { ... };` the block, vs. a hypothetical plain field named `env`)
by additionally checking that `{` follows the `=`.
